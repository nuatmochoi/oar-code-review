# 신규 6계열 B/P/R 본실험 결과

**실제 LSP 호출 참조를 더한 R의 추가 이득은 이번 실험에서 확인되지 않았다.** 주 비교 R−P에서 근거 있는 버그 검출은 동일한 11/18, 양방향 성공은 P 6/18에서 R 5/18이었다. 기존 B는 양방향 성공 8/18로 가장 높았다. 기본 B를 유지하고 P/R의 일괄 적용은 보류하는 판단이 적절하다.

이전 개발 11계열에서 보충 방식이 좋아 보였지만, 새 6계열에서 같은 효과가 재현되지는 않았다. 작은 계열 수와 모델 변동 때문에 R이 일반적으로 나쁘다고 단정할 수는 없다. 현재 결과는 추가 조회 비용을 정당화할 성공률 개선의 근거가 부족하다는 뜻이다.

## 고정한 비교와 실행

- **B:** 기존 선택 정책, 실제 LSP 정의 조회 최대 12회.
- **P:** 같은 B 소스/조회 결과에서 기존 중요 근거를 보호하고, 빠진 변경 분기·기본 인자·인자 기반 생성 호출·import를 보충.
- **R:** 완성된 P에서 그대로 시작하고, 실제 LSP `textDocument/references` 최대 3회로 찾은 caller 소스·관련 import·정적 관측만 추가. P가 보호하거나 추가한 소스 줄은 유지.

주 비교는 R−P, 보조 비교는 P−B다. R−P는 참조 조회의 추가 정적 관측과 소스 보충의 결합 효과이며, 두 채널을 분리한 효과가 아니다. 세 조건 모두 소스 최대 1,600토큰, 정적 관측 최대 400토큰, 조회 최대 15회다. B/P는 추가 3회 조회 예산을 사용하지 않으므로 R의 실제 비용이 더 든다. 소스 예산은 diff·공개 계약·공통 프롬프트를 포함한 총 입력 예산이 아니다.

프로젝트에서 기존 리뷰 계열과 겹치지 않는 6개 실제 PR을 사용했다. 각 PR의 공식 수정 방향과 명시적인 reverse control을 각각 3회 평가했다. 6 × 2방향 × 3조건 × 3반복 = **108 logical reviews**다. N03의 B/P 입력이 같은 방향/반복에서 완전히 같아 6개 응답을 공유했으므로 **102 physical calls**를 실행했다. 반복 간 공유는 없다.

모델은 gpt-5.6-sol, low reasoning, 도구 호출 0회, 재시도 0회, workers 4다. provider seed 통제는 없다. 입력·코드·선정·공개 계약·witness·schema·native trace를 응답 전에 고정했고, 이전 모델 리뷰 결과를 재사용하지 않았다. 새 PR은 프로젝트 기준으로 미평가였으며 모델 사전학습에 없는 데이터라는 주장은 아니다. 기존 세 저장소의 다른 PR이므로 새 저장소 일반화 실험도 아니다.

## 전체 결과

unsafe 방향은 공급 근거로 새 회귀를 설명한 issue가 있어야 검출 성공이다. safe 방향은 계약에 대한 근거 있는 `no_supported_issue`가 필요하다. 같은 반복에서 두 방향을 모두 맞혀야 양방향 성공이다. `insufficient_evidence`는 성공으로 세지 않고 분모에 남긴다.

| 지표 | B | P | R |
|---|---:|---:|---:|
| 근거 있는 버그 검출 | 9/18 | 11/18 | 11/18 |
| 안전 방향 오탐 | 0/18 | 0/18 | 0/18 |
| **양방향 성공** | **8/18** | **6/18** | **5/18** |
| 개별 방향 정답 | 18/36 | 17/36 | 16/36 |
| 판단 유보 | 18/36 | 19/36 | 20/36 |
| 운영 검증 통과 | 36/36 | 36/36 | 36/36 |

P−B는 검출 +2회지만 양방향 성공 −2회였다. R−P는 검출 차이 0회, 양방향 성공 −1회였다. 반복을 맞춘 양방향 결과에서 P가 B보다 새로 성공한 경우는 0회, 잃은 경우는 2회다. R이 P보다 새로 성공한 경우도 0회, 잃은 경우는 1회다. 반복 번호는 비교를 위한 그룹이며 동일 provider seed로 실행한 짝은 아니다.

## 사례별 결과

각 칸은 **버그 검출 / 양방향 성공**, 각각 최대 3회다.

| 계열 | 고정 계약 | B | P | R |
|---|---|---:|---:|---:|
| N01 Requests 6028 | URL helper의 인증 정보 보존 | 1 / 0 | 2 / 0 | 2 / 0 |
| N02 pytest 10356 | 다중 상속 클래스의 MRO 마커 취합 | 3 / 3 | 3 / 3 | 3 / 3 |
| N03 pytest 7490 | 실행 중 추가한 xfail의 최종 보고 | 0 / 0 | 0 / 0 | 0 / 0 |
| N04 SymPy 12096 | 구현 함수 f(g(2)).evalf()의 재귀 평가 | 0 / 0 | 0 / 0 | 0 / 0 |
| N05 SymPy 14531 | Eq/Limit의 printer 설정 전파 | 2 / 2 | 3 / 0 | 3 / 0 |
| N06 SymPy 20154 | iterator가 넘긴 dict의 값/독립성 보존 | 3 / 3 | 3 / 3 | 3 / 2 |

**N02:** R은 실제 참조로 decorator의 `__call__ → store_mark` 소스도 보충했지만, B/P도 이미 공개 three-class 계약과 직접 바뀐 getter/storage 코드로 양방향 3/3이었다. 추가 소스가 점수 상승으로 이어지지 않았다.

**N03:** 모든 조건에서 failed/xfailed를 결정하는 후속 보고 코드가 부족하다는 유보가 반복됐다. post-yield 재평가 유무를 알아도 reporting consumer가 보이지 않는다는 답변이다. R의 참조 후보가 일부 있어도 그 공백을 닫지 못했다. B/P는 동일 입력을 공유한 조건이므로 독립 응답처럼 해석하지 않는다.

**N04:** 함수 인자를 먼저 평가하는 변경과 `_imp_` 구현 연결은 보이지만, `Float` 생성/숫자 변환과 최종 evalf 결과를 뒷받침하는 근거가 부족하다는 유보가 이어졌다. B의 안전 방향 1회만 수정으로 판단했고, unsafe 검출은 모두 0회였다. R은 추가 caller를 넣었지만 필요한 변환 구현을 공급하지 못했다.

**N05:** P/R은 raw interpolation이 active printer를 우회하는 버그 방향을 3/3 찾았다. 그러나 안전 방향에서는 실행 분기·active setting 동작·최종 문자열이 확정되지 않았다고 모두 유보했다. B는 안전 방향 2회와 해당 버그 방향 2회를 함께 맞혔다. P에서도 head `_print_Limit` 전체 코드는 유지돼 있었으므로, 안전 성공 감소를 그 함수가 삭제됐기 때문이라고 설명할 수 없다. 넓은 공식 patch의 다른 메서드 조각과 부분 코드가 추가된 컨텍스트 변화가 있었으나 어떤 조각이 유보를 유발했는지는 이 실험으로 확정하지 않았다. R의 참조 스케줄은 전체 변경 함수 후보를 소비하며 Eq/Limit에 필요한 후보를 확보하지 못했다.

**N06:** B/P는 3/3, R은 2/3 양방향 성공이었다. `N06_b_R_r2`가 `ms.copy`의 runtime binding을 unknown으로 보아 안전 방향을 유보했다. 다른 두 R 반복은 복사로 기존 dict 결과가 보존된다고 판단했다. 이 한 응답이 R−P의 양방향 −1회를 설명한다. 일반적인 품질 하락이나 인과 효과로 단정하지 않는다.

**N01:** unsafe의 직접 auth 재조립 제거는 일부 답변이 검출했다. safe 방향은 세 조건 모두 parser 값과 최종 URL이 확정되지 않았다고 유보했다. HTTP 407/200은 평가 대상이 아니며 외부 프록시 요청을 하지 않았다.

## 근거 수준과 판정 한계

작성자가 계열과 정답 방향을 아는 상태에서 108건 모두 수동 검토했다. 공개된 고정 계약, 제공된 source/diff/정적 관측, 표준 Python 의미로 직접 변경의 원인을 설명하는 경우를 인정했다. 숨긴 witness를 모델의 근거 공백을 메우는 데 사용하지 않았다. issue claim의 원인 설명에 추가로 근거 없는 원인이 있는 경우나 scope 밖 문제를 성공으로 세는 기준은 적용하지 않았고, 이번 응답에서는 그런 추가 주장을 발견하지 않았다.

이 판정은 **공개 계약에 대한 직접 코드의 인과 진단**이며, 모든 런타임 binding/dispatch를 독립 인증한 점수가 아니다. 특히 다음 범위를 구분했다.

- N01의 공급 diff에는 `parse_url`의 netloc에 auth가 포함되지 않는다는 설명과 제거된 auth 재조립이 있다. 이를 고정된 인증 URL helper 계약의 원인으로 인정했지만 외부 parser·serializer 구현 전체나 HTTP 결과를 인증하지 않았다.
- N02는 선언된 decorator fixture와 변경된 store/getter/normalize 및 Python MRO로 직접 원인을 판정했다. B/P의 모든 public decorator dispatch 구현이 공급된 것은 아니다.
- N05는 고정 Eq/Limit 설정 계약과 active `self._print` 대 raw formatting 변경을 판정했다. 완전한 printer dispatch/settings 실행과 정확한 전체 출력 경로를 독립 증명한 것은 아니다.

이 범위는 수동 판정 메모에도 기록했다. 안전 방향에서 contract 자체를 unknown으로 남기며 `insufficient_evidence`를 반환한 답변에는 성공 점수를 주지 않았다. 6개 계열의 3회 반복은 18개 독립 PR이 아니다. 비블라인드 작성자 판정, 명시적 reverse control, 작은 표본, provider seed 미통제 때문에 통계적 우위·열위나 일반화를 주장하지 않는다. N06처럼 공식 diff의 문서에 aliasing 예제가 들어 있는 경우도 있어, 숨겨진 버그를 독립 발견하는 benchmark로 해석하지 않는다.

## 실행·보존 검증

모델 호출/스키마 102/102 성공, 108/108 논리 응답 운영 검증 통과, 인용/ledger 오류 0, 누락 0, 모델 도구 호출 0, 재시도 0이었다. 고정 파일과 준비 seal, workspace source hash가 유지됐다. P의 보호/추가 소스 단위 111개는 R에서도 같은 줄로 유지됐으며 소스/관측 예산을 통과했다. issue 39개의 논리적 file/line 존재를 확인했다. 위치 정확도의 별도 일치율을 측정한 것은 아니다.

입력 준비에서 공통 native 정의 조회 135회를 수행해 세 조건에서 공유했고, R을 위한 native 참조 조회는 32회였다. 참조 조회 중 in-corpus 후보가 있었던 것은 14회이며 오류는 없었다. 통합검증 fixture 조회는 이 준비 수와 별도다. R의 소스가 P와 달라진 것은 N02/N04/N06의 양방향 6/12 입력이다. 나머지는 추가 정적 관측만 달랐다. 참조를 찾은 사례만 골라 주 비교로 바꾸지 않았다.

## 적용 판단과 다음 개선

**B를 유지한다.** P/R은 기본 파이프라인으로 승격하지 않는다. 버그 방향 검출만 보면 P/R이 +2회였지만, 안전한 수정의 판정이 줄고 주 지표인 양방향 성공은 개선되지 않았다. 이전 개발 사례의 향상을 일반적인 추가 참조 효과로 해석해서는 안 된다.

다음 개선을 한다면 무작정 caller 수를 늘리기보다 **부족한 연결을 지정해서 공급하는 방식**이 우선이다. N03에는 xfail 상태의 reporting consumer, N04에는 Float/숫자 변환 구현, N05에는 해당 설정을 사용하는 public printer dispatch가 필요하다. 추가 후보가 고정 계약의 어느 연결 공백을 닫는지 확인하고, 닫지 못하면 기존 근거를 교체하지 않는 선택 정책을 검토할 만하다. 이 제안은 이번 본실험 후 분석이며 아직 구현하거나 검증한 개선이 아니다.

자료: 사전 조건, 집계, 응답 감사, 수동 판정 메모, 최종 검증. 준비 보고서와 seal은 변경하지 않았고, 원본 응답·trace·108개 고정 입력은 그대로 보존했다.
