# V3 코드 리뷰 비교 실험 — B0 포함 최종 F1

2026-10-29 · 같은 Python 개발 PR 12개 × 안전/결함 두 방향 × 5조건 × 1반복 = **새 리뷰 120개**. 병렬 2개로 실행했으며 모델 실행 구간은 약 44분 18초였다. 과거 B0/F/G/V2 결과는 보존했고 이번 표에 섞지 않았다.

**CB는 근거 충족 F1이 36.36%로 L과 같아 주 지표 향상을 달성하지 못했다.** 원인 수준 F1은 L 63.64% → CB 81.82%로 올랐고 출력·상태 실패는 4건 → 0건, 안전 오경고는 1건 → 0건이었다. 그러나 **B0도 원인 F1 81.82%**이며 호출 수는 24회로 CB 40회보다 적었다. 따라서 이번 결과만으로 CB를 성능 개선 방식으로 채택하지 않는다.

## F1 비교 — 모든 조건을 한 표에

| 조건 | 근거 TP/FP/FN | 근거 P/R (%) | 근거 F1 (%) | 원인 TP/FP/FN | 원인 F1 (%) | 안전 오경고 /12 | 출력·상태 실패 /24 |
|---|---:|---:|---:|---:|---:|---:|---:|
| **B0 · 계약+diff** | 0/10/12 | 0.00/0.00 | **0.00** | 9/1/3 | **81.82** | 0/12 | 0/24 |
| L · 기존 AR 탐색 | 4/6/8 | 40.00/33.33 | **36.36** | 7/3/5 | **63.64** | 1/12 | 4/24 |
| C · L+controller | 3/6/9 | 33.33/25.00 | **28.57** | 8/1/4 | **76.19** | 0/12 | 0/24 |
| B · L+범위·본문 조회 | 2/10/10 | 16.67/16.67 | **16.67** | 6/6/6 | **50.00** | 1/12 | 5/24 |
| **CB · 두 개선 결합** | 4/6/8 | 40.00/33.33 | **36.36** | 9/1/3 | **81.82** | 0/12 | 0/24 |

P는 precision, R은 recall이다. F1은 **precision과 recall의 조화평균**이며 `F1 = 2TP / (2TP + FP + FN)`이다. 각 조건의 결함 방향은 12개로 고정하고 `FN = 12 − TP`, `FP = 원시 최종 보고 수 − TP`로 계산했다. 출력 검증 실패의 명시적 보고도 분모에 남겼다. 중간 후보나 요약의 정답을 최종 finding으로 승격하지 않았다.

- **근거 F1:** 정확한 원인·조건·영향, 사전에 정한 필수 코드 연결의 실제 공급, 최종 인용·보고 유효성을 모두 만족해야 TP다.
- **원인 F1:** 필요한 외부 연결이 부족해도 정확한 국소 원인을 유효한 최종 finding으로 보고하면 TP다. 형식·최종 상태 실패는 이 지표에서도 TP가 아니다.
- **안전 오경고:** 실제 안전 방향에서 raw finding을 낸 리뷰 수다. 게이트가 막아도 오경고로 남긴다.

**B0의 근거 F1 0%는 결함을 전혀 못 찾았다는 뜻이 아니다.** B0는 원인 9개를 맞혔지만 그 9개에 필요한 저장소 연결은 diff만으로 확인되지 않았다. 근거 기준의 FP에는 잘못된 원인뿐 아니라 필수 근거 부족·무효 보고도 포함된다. 이를 일반적인 “안전한 코드에 대한 오경고”와 혼동하지 않도록 위 표에 원인 F1과 안전 오경고를 함께 표시했다. diff에 증명이 완결되면 B0도 인정한다. 실제 N03 안전 방향은 B0 역시 근거 충족 안전으로 판정됐다.

## 무엇을 비교했나

- **B0:** 공통 공개 계약·고정 입력·diff만 제공. 추가 source seed, AST/LSP, 검색, 후보 ledger, C/B 기능이 없다. 제품의 탐색 비활성 리뷰 분기에서 한 번 판단한다.
- **L:** V2의 A+R 기반 agentic 탐색을 이번 조건으로 새로 실행했다. 조회 우선순위 A와 근거·후보 상태 ledger R이 포함된다. 원본 제품 P나 diff-only가 아니다.
- **C:** L에 controller 소유 근거 handle, 후보/의무 ID 및 상태 변경 기록 생성을 추가했다. 의미 판단과 근거의 충분성 판단은 모델에 남긴다.
- **B:** L에 명시 경로 범위의 심볼 조회와 위치에서 실제 본문을 읽는 기능을 추가했다. 자동 읽기도 조회 예산에 포함한다.
- **CB:** C와 B를 함께 적용했다.

모델은 모두 `gpt-5.6-sol`, reasoning `low`다. 호출 상한 3회, 후속 2라운드, pre-gap 포함 조회 6회·배치당 3회, 보호된 seed를 포함한 추가 source 합집합 5,200 o200k tokens, metadata 누적 800, 상태 1,600의 같은 상한을 사용했다. B0는 탐색이 없어 1회에 종료하며 다른 조건도 조기 종료한다. **동일 상한이지 동일 실제 계산량은 아니다.**

공유 24개 prepared input은 V2와 바이트 단위로 같다. L/C/B/CB의 seed와 workspace revision은 같고 B0는 source seed를 제거한다. L의 스크립트 입력은 V2 AR 대비 20/20 stages, 136/136 digest fields가 일치했다. 실제 Pyright를 사용했고 AST 범위 fallback은 별도 기록했다. SCIP 인덱싱·강화학습·새 런타임 실행 증명은 이번 개입에 없다. B0→L에는 여러 요소가 함께 추가되므로 이 차이를 AST나 LSP 하나의 효과라고 해석할 수 없다.

주 비교 **CB−L의 근거 F1 차이는 0.00pp**, PR 단위 paired bootstrap 95% CI는 **−5.01~+4.14pp**다. 원인 F1 차이는 +18.18pp이나 CI가 0.00~+40.91pp다. CB−B0 원인 F1 차이도 0.00pp (−15.65~+15.65pp)다.

12개 PR의 두 방향과 모든 조건을 함께 재표집하는 cluster bootstrap 10,000회, seed 2026102603을 사용했다. 구간은 PR 구성의 불확실성을 보여주며 모델의 반복 실행 변동은 1반복으로 측정하지 못한다. 아래 보조 비교는 다중 비교 보정을 하지 않았으며 독립적인 확증 결과로 해석하지 않는다.

## 개선된 부분과 남은 한계

**최종 보고 안정성은 개선됐다.** C와 CB는 모두 출력·상태 실패가 0건이다. L은 4건, B는 5건이었다. 모델 전송 166회는 모두 정상으로, 이 9건은 네트워크/호출 실패가 아니라 후보 상태·변경 기록·보고 가능성 검증 실패다. C에서 변경 기록 10개, CB에서 12개를 controller가 생성했다.

**필수 근거를 갖춘 결함의 범위는 늘지 않았다.** L과 CB의 근거 TP 4개는 모두 N04 비동기 fallback, N05 precision=0, N09 문자열 분모 반복, N12 빈 이름 guard 제거로 같은 집합이다. CB가 원인 TP를 추가한 N02 deepcopy와 N07 rank-zero Array도 상속 또는 순회 연결이 부족하여 근거 TP가 되지 못했다.

- **N04:** B/CB는 실제 `http_method_names` 값과 관련 본문을 확보했다. B는 정확한 raw 원인·근거를 얻고도 변경 기록 누락으로 실패했고 CB는 유효하게 보고했다. L도 해당 본문을 직접 조회해 같은 결함을 근거 TP로 잡았으므로 CB만의 새 탐지로 세지 않는다.
- **N02/N10:** B의 추가 본문이 각각 다른 Field 하위 타입이나 Curve 사용처로 향했다. 필요한 CharField 상속·override 또는 Point factory/len/iter 연결을 채우지 못했다. “본문을 읽음”과 “필요한 본문을 읽음”은 달랐다.
- **N06:** B0/B는 finite 가정 전달 소실을 원인 수준으로 탐지했다. L/CB는 보류했고 C는 positive만으로 finite가 보존된다고 잘못 단정했다. 탐색 또는 controller를 추가하면 항상 개선되는 결과가 아니다.
- **N03:** 결함 방향의 다섯 조건 모두 `functools.wraps` 자체가 누락 metadata 때문에 실패한다고 설명했다. 실제 목표는 사용자 wrapper의 `f.__name__` 접근 실패다. 잘못된 원인을 정탐으로 인정하지 않았다.

원시 정답을 진단용으로 따로 보면 L/C/B/CB의 근거 충족 원인 수는 4/3/4/4, 국소 원인 수는 8/8/10/9다. B의 근거 원인 4개 중 유효 최종 보고는 2개뿐이었다. 이 진단값은 F1의 TP를 대체하지 않는다. 근거 충족 안전 리뷰는 B0 1/12, 나머지 각 4/12이며, 보류 횟수는 B0/L/C/B/CB 순서로 2/2/2/1/3건이다.

## 채택 판단과 다음 개선

사전 채택 후보 조건은 “CB의 근거 F1이 L보다 높고 안전 오경고가 증가하지 않음”이었다. **근거 F1이 동일하므로 조건 미충족이며 채택 보류**다. 원본 제품에는 배포·반영하지 않았고 실험 구현과 결과를 보존했다. C의 기록 자동화는 실패 감소의 유망한 공학적 개선이지만, 단독 C의 근거 F1은 L보다 낮아 전체 성능 향상으로 주장할 수 없다.

다음 개선 우선순위는 다음과 같다. 이번 실행 중에는 적용하지 않았다.

1. 본문 읽기 대상을 일반 참조 순서보다 **아직 확인하지 못한 결함 주장과 필수 연결**에 맞춰 고른다. 예를 들어 CharField 상속·override, VariableNode→렌더링 helper, Array/Point의 실제 len·iter를 해결하는 조회를 우선하고 무관한 사용처로 예산을 소모하지 않게 한다.
2. B0에서 얻은 원인 후보를 검증할 가설로 보존하고, 추가 문맥이 이를 지지·반박·미해결 중 어디로 바꿨는지 추적한다. 근거 없는 안전 단정으로 후보가 사라지는 N06 같은 경로를 줄이는지 별도 실험한다.
3. 방법·기준을 고정한 뒤 새 PR과 반복 실행에서 비용을 맞춘 대조군까지 비교한다. 먼저 근거 F1 향상이 반복 확인돼야 논문 method의 성능 주장으로 채택한다.

이번 자료는 여러 차례 관찰한 같은 12개 Python 개발 PR을 사용한 비맹검 AI 저자 평가다. 협업 AI의 교차검토를 했지만 독립 인간·holdout 평가가 아니다. 공개 계약과 구체적인 고정 입력도 제공했으므로 일반 MR 리뷰보다 좁은 문제다. 근거 F1은 사전 사례별 필요 근거 기준이며 모든 간접 호출을 완전히 증명하는 형식 검증 지표가 아니다. N09의 Integer 생성자 전체 미공급과 사전 좁은 증명 범위는 별도 판정 기록에 남겼다.
