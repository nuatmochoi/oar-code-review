# 기존 근거 보호 + 실제 LSP 호출 참조 보충 비교

개발 11계열의 반복 비교에서 새 방식 F의 양방향 성공은 **15/33**, 대조군 B15는 **9/33**이었다. 근거 있는 버그 검출은 20/33 대 17/33이었다. 다만 F에 오탐 1건이 생겼고, 이전에 평가했던 확인 4계열에서는 두 방식 모두 양방향 성공 1/4로 개선이 없었다. **부족한 컨텍스트를 보충하는 후보로는 유지하되, 기본 방식 전체를 교체할 근거는 아직 부족하다.**

## 무엇을 비교했나

- B15: 이전 B의 소스와 12회 정의 조회 기록을 공통 시작점으로 사용한다. 아직 조회하지 않은 호출 위치에서 실제 LSP 정의 조회를 최대 3회 추가한다. 전체 소스 단위를 예산 내에서만 추가하며 기존 소스는 제거하지 않는다.
- F: 같은 시작점에서 실제 Pyright `textDocument/references`를 최대 3회 추가한다. 기존 변경 함수·직접 호출 연결·정의 조회 결과 등 보호 대상은 유지하고, 보호되지 않은 검색 결과만 제거할 수 있다. 빠진 변경 분기·기본 인자·인자 기반 생성 호출과 LSP가 반환한 참조 위치 주변 코드를 부분적으로 보충한다.

두 방식 모두 소스 1,600토큰, 정적 관측 400토큰, 조회 최대 15회다. 공통 관측 280토큰과 추가 관측 120토큰으로 구성했다. 소스 예산은 diff·계약·공통 프롬프트를 포함한 전체 입력 예산이 아니다. 실제 조회 수는 후보 유무에 따라 달랐다.

Pyright 1.1.414의 실제 JSON-RPC 응답을 기록했다. 호출 참조를 소스 후보로 넣는 기준은 LSP 결과다. AST는 변경 위치·분기·인자·소스 조각 선택과 일부 기존 근거 보호에 사용한다. 기존 호출 보호에는 같은 이름의 호출을 찾는 휴리스틱도 남아 있다. 정적 참조는 런타임 receiver·인자 값·dispatch를 증명하지 않는다.

모델은 `gpt-5.6-sol`, low reasoning, 도구 0회, 재시도 0회, 동시 실행 4개다. 기존 11계열은 양방향 각각 3회, 확인 4계열은 각각 1회 평가해 **148건 모두 새 모델 응답**을 받았다. 이전 B의 리뷰 결과를 재사용하지 않았다. 두 방식의 소스·조회 기록·프롬프트를 모델 호출 전에 고정했다. 확인 4계열은 이미 여러 차례 평가했으므로 미관측 holdout으로 해석하지 않는다.

## 도움이 된 부분과 남은 실패

**E11이 가장 명확한 보충 사례다.** 실제 `symbols(names, *, cls=Symbol, **args)` 선언, 재귀 호출, 문자열 분기의 `cls(...)` 생성 지점이 함께 들어갔다. 이전 부분 코드 방식에서 빠졌던 생성 분기가 보이고, F는 안전 방향 3회 모두 근거 있는 수정으로 판단했다. 버그 검출은 양쪽 모두 3/3이었다.

**E08은 기존 근거 손실을 막았다.** B에 있던 `caplog` fixture의 `yield result` 뒤 `result._finalize()`와 변경된 level 저장/복원 소스가 F에도 유지됐다. 양방향 성공은 두 방식 모두 3/3이다. 이번에는 호출 연결을 실제 소스에서 볼 수 있지만, 전체 pytest 실행 경로를 독립적으로 인증한 결과는 아니다. 공개 두 테스트 계약과 직접 변경 구현을 바탕으로 같은 기준을 적용했다.

E10은 F의 버그 검출이 2/3, B15는 0/3이었다. F는 LSP가 반환한 caller와 import도 보충했다. 다만 바뀐 단일 메서드의 직접 동작은 대조군에도 보이며, 모델의 유보 감소를 특정 추가 조각 하나의 인과 효과로 확정할 수 없다. E03·E06·E12에서도 양방향 성공이 각각 1회 증가했다.

**Requests의 값·binding 공백은 남았다.** E01의 참조 caller는 헤더 인자 표현식을 보여 주지만, 실제 request 구성과 mapping 값 및 downstream 직렬화는 생략됐다. F의 `E01_a_F_r2`는 이를 넘어서 `Accept-Encoding: None`이 전송된다고 단정해 검출 점수에서 제외했다. E02의 parser 결과를 단정한 안전 답변도 성공에서 제외했다.

F의 유일한 안전 방향 오탐 `E04_a_F_r3`는 보이지 않는 import를 없다고 간주해 `to_native_string`의 NameError를 주장했다. 부분 코드의 생략은 이름이 미정의라는 증거가 아니다. 기존에 보이는 변경 함수는 보충 후보에서 제외될 수 있어, 그 함수가 쓰는 누락 import 연결도 함께 보충되지 않는 설계 한계가 있다.

B15의 `E06_a_B15_r1`은 원인 설명은 맞지만 issue를 연결한 ledger의 비교가 `changed`가 아니어서 운영 검증에 실패했다. 이를 고치거나 재호출하지 않았다. 이 실패를 의미 판정만으로 제외하면 대조군 검출은 18/33이지만, 주 결과는 사전 운영 기준을 유지한 17/33이다. 양방향 성공 수에는 영향을 주지 않는다.

## 조회·소스·실행 검증

공통 B 조회 기록 **360회**를 두 방식에서 재사용했다. 이번 입력 준비에서 새로 실행한 조회는 B15 정의 75회와 F 참조 83회, 총 **158회**다. 초기화·프로토콜 통신과 통합검증 fixture 조회는 이 준비 조회 수에 포함하지 않는다. 통합검증은 준비 전에 두 차례 실행했으며 저장된 마지막 trace에는 참조 조회 2회가 있다.

B15의 추가 정의 조회는 75회 중 2회에서 in-corpus 후보를 찾았지만 기존 포함/예산 때문에 30개 모두 기존 B 소스와 같았다. 관측 구성은 이전 B와 다르므로 이전 B 점수를 직접 대조군 점수로 대체할 수 없다. F는 83회 중 52회에서 소스 후보를 찾았고 26/30 입력의 소스를 보충했다. 반환된 참조가 모두 관련 런타임 경로라는 뜻은 아니다.

F는 30개 입력을 합쳐 기존 보호 소스 단위 179개를 원래 줄 그대로 유지했다. 보호되지 않은 단위 101개를 제거했고, 최종 입력에 기존 B에 없던 단위 193개를 넣었다. 대부분 부분 코드나 import이며 모두 유용한 근거라고 세지 않았다. `fragment_selections`는 시도 이력을 포함할 수 있으므로 최종 `source_lines`, `additions`, `evicted_ids`를 기준으로 확인했다.

실제 LSP 통합검증에서 동일 이름의 다른 메서드 caller 제외, native caller 사용, 보호 소스 유지, 빠진 분기·인자 기반 생성 호출 포함, 토큰 제한을 확인했다. 본실험에서는 다음이 통과했다.

- 모델 호출·스키마 응답 148/148 성공, 모델 도구 호출 0, 누락 0, 수동 검토 148/148.
- 고정 코드·입력 준비 파일과 workspace 소스 해시 유지.
- 소스 1,600/관측 400토큰, 공통 12 + 추가 최대 3회 조회 제한.
- 보호한 기존 소스 줄 그대로 유지, 추가 native 조회 오류 0.
- 보고된 issue 42개의 파일과 줄 존재. 위치의 정확한 일치율은 별도 측정하지 않았다.

작성자가 결과와 계열을 아는 상태에서 채점했다. 숨긴 witness로 모델의 부족한 근거를 메우지 않았다. 모델 seed 통제는 없으며, 소수 계열 반복 결과라 통계적 우위나 일반화된 성능 향상을 주장하지 않는다. F는 **보호 + 부분 코드 + 참조 조회 + import 보충의 결합**이므로 참조 조회 단독 효과나 논문의 원 실험 재현으로 해석하지 않는다.

## 적용 판단

현재 기본 B는 유지하고 F를 **큰 변경 함수가 소스 예산으로 빠진 경우의 보충 후보**로 두는 것이 적절하다. 가장 유망한 부분은 기존 근거를 보호한 채 signature·기본 인자·재귀 전달·실제 생성 분기를 함께 넣는 선택 정책이다. 다음 분리 비교가 필요하다면 보호+분기 보충만 하는 arm과 실제 참조를 더하는 arm을 비교해, 이번 6회 양방향 성공 증가가 어디서 왔는지 구분해야 한다. import 연결과 실제 인자 값 확인도 아직 해결할 대상이다.

세부 근거: 고정 실험 조건, 판정 기준, 응답 감사, 수동 판정 메모, 집계, 검증. 원본 응답은 `raw/`, 고정 프롬프트는 `inputs/`, native 기록은 `lsp_traces/`에 보존했다.
