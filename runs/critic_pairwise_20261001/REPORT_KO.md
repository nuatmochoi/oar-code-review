# 제한된 critic과 후보 쌍 비교 실험

**새 변경 6쌍에서는 기본 리뷰·critic·쌍 비교가 모두 6/6쌍을 맞혀 추가 성능 이득이 확인되지 않았다. 실제 경로 진단에서는 critic이 안전 조건 하나를 불필요하게 기권했고, 쌍 비교는 후보 간 불일치 한 건에서 근거 있는 결함 리뷰를 선택했다.** 사후 기능 진단에서는 critic이 잘못된 초안3/4개를 회복했고, 쌍 비교가 올바른 후보를 양쪽 표시 순서에서8/8회 선택했다. 기능 진단은 일반 성능 점수와 합산하지 않는다.

현재 기본 정책으로는 근거표를 포함한 단일 리뷰를 유지하는 편이 낫다. 2번 critic은 실제 입력을 잘못 가정한 경고를 점검하는 제한된 용도로, 3번 쌍 비교는 후보가 불일치할 때의 선택 방식 후보로 남긴다. 전체 요청마다 추가 호출하는 정책의 이득은 이번 결과로 입증되지 않았다. 이런 선택적 호출 정책 자체도 이번에 구현·평가한 것은 아니다.

## 비교 방법과 범위

같은 gpt-5.6-sol low, 같은 소스 근거, 같은 factual ledger+최종 review schema를 사용했다. source cap은4,000 reference tokens이고 실제 최대2,851이었다. 이전1,600-token 검색 실험과 직접적인 동일 조건 비교가 아니다. 사전 선정한 실제 함수 본문과 진입 코드가 세 조건에 똑같이 제공되므로 이번 비교 대상은 **검토·선택 단계**다.

| 조건 | 흐름 | 최종 결과 한 건당 호출 |
|---|---|---:|
| 기본 | 근거표+리뷰 생성 | 1 |
| critic | 기본 초안을 동일 근거로 검증·수정 | 2 |
| 쌍 비교 | 기본+동일 prompt의 독립 후보 → 익명 두 후보 비교·선택 | 3 |

critic은 receiver·설정·입력·분기·base/head 차이에 집중하고, 근거 없는 가정을 제거한다. 별도 최종 재작성 호출은 없다. 쌍 비교에는 critic 출력을 넣지 않아 두 효과를 분리했다. 후보 표시 순서는 사전 고정했고, tie는 baseline, insufficient는 기권으로 처리했다. 선택 후 rewriting은 없다.

[Adversarial Review](https://arxiv.org/html/2608.18167v1)의 근거 제한 검토와 [V1](https://proceedings.mlr.press/v306/singh26b.html)의 쌍 비교 아이디어를 적용한 추론 실험이다. Adversarial Review 전체 상호작용 구조나 V1의 불확실성 기반 tournament·PairRL을 재현하지 않았다.

## 새 통제 변경6쌍

같은 ComfyUI 저장소의 pinned source에서 이전과 다른 변경을 주입했다. concatenate 순서, length의 whitespace 제거, regex search→match, regex replacement count 무시, capitalize→lower, Ends With→Starts With다. 실제 execute AST를 base/head × 안전/결함 입력 ×2반복=48회 실행했고 예상 차이를 확인했다. io.NodeOutput은 tuple 경계로 대체했으며 ComfyUI 전체 서버/생성자/그래프 실행은 재현하지 않았다.

| 조건 | 근거 있는 결함 검출 | 안전 오탐 | 기권 | 안전·결함 둘 다 맞힌 쌍 |
|---|---:|---:|---:|---:|
| 기본 | 6/6 | 0/6 | 0/12 | 6/6 |
| critic | 6/6 | 0/6 | 0/12 | 6/6 |
| 쌍 비교 | 6/6 | 0/6 | 0/12 | 6/6 |

독립 두 번째 후보도12/12 world를 맞혔다. 따라서 올바른 후보 포함률12/12, 포함 시 선택 성공12/12이지만, **정답 여부가 다른 후보가 없었다.** 모든 새 world에서 selector는 tie를 냈다. 이 결과는 선택기의 추가 판별력을 입증하지 않는다. 표시 순서를 바꾼4회도 모두 tie였으므로 순서 편향을 강하게 배제하는 증거도 아니다.

이 사례들은 기존 저장소와 일부 이미 조사한 class를 사용했다. 새 변경이지만 독립 저장소 holdout/자연 PR 벤치마크가 아니며, 짧은 함수와 단순 주입 변경에서의 결과다.

## 실제 경로 진단4 world

D04는 실제 backend 선택과 kb_app.update 호출을 연결한 Infinity 설정의 요청0/2 쌍이다. D08은 실제 `/view`의 filename=missing.png/filename 없는 두 안전 입력이다. 앞서 실행한12회 source witness를 재사용했으며 이번 새48회에 합산하지 않았다. D08은 양쪽 모두 음성 대조군이고 결함 pair 분모에는 넣지 않는다.

| 조건 | 결함 검출 | 안전 오탐 | 기권 | 맞힌 world |
|---|---:|---:|---:|---:|
| 기본 | 1/1 | 0/3 | 0/4 | 4/4 |
| critic | 1/1 | 0/3 | 1/4 | 3/4 |
| 독립 두 번째 후보 | 0/1 | 0/3 | 1/4 | 3/4 |
| 쌍 비교 | 1/1 | 0/3 | 0/4 | 4/4 |

critic은 안전 요청 pagerank2가 remove 분기를 실행하지 않고 base/head가 같은 값을 제출한다는 점을 확인하면서도, 외부 DB 결과가 알려지지 않았다는 이유로 기권했다. 이 고정 입력에서 변경 분기가 제외되는 판정에는 DB의 최종 응답이 필요하지 않으므로 불필요한 기권으로 판정했다.

결함 요청 pagerank0의 독립 후보는 head가 비컬럼 `remove` 키를 제출한다는 사실을 인정하고도 최종 DB/API 결과가 없다는 이유로 기권했다. selector는 기본 리뷰를 선택했다. 근거 있는 결함 리뷰는 스키마에 없는 키가 제출되는 사실만 보고하고, 실제 DB 예외/API 응답은 미확정으로 남겼다. 따라서 이 선택은 후보의 과도한 기권을 피한 사례다. 다만 기본 리뷰가 이미 맞았으므로 기본 대비 점수 증가는 아니다.

안전 요청의 기본 근거표는 외부 table.update 성공을 확인하지 않고 API 완료를 단정한 문장이 있었다. 로컬 변경 분기 제외라는 판정은 유효하지만 이 문장은 미입증이다. 독립 후보가 외부 결과를 미확정으로 표현했고 selector는 그 후보를 선택했다. 판정 점수와 근거표의 표현 정확도를 구분해 기록했다.

## 사후 기능 진단 — 의도적으로 틀린 초안/후보

새6쌍 기본 리뷰가 모두 맞은 것을 확인한 뒤 별도 protocol/freeze로 추가한 기능 시험이다. 작성자가 공개 입력·소스와 모순되는 초안을 만들었고, 모델에는 정답/오답 이름이나 기대 라벨을 주지 않았다. 본실험의 정답 baseline과 작성자 오답을 두 순서로 제시했다. 자연 발생 오답 개선이나 독립 성능 검증으로 해석하지 않는다.

| 잘못된 초안 | critic 수정 | 쌍 비교: good 왼쪽/오른쪽 |
|---|---|---|
| D04 결함: head도 remove를 삭제한다고 주장 | 제출값은 바로잡았지만 기권 | 모두 good 선택 |
| D04 안전: 실제 pagerank2를0으로 바꿔 경고 | 올바른 no_supported_issue | 모두 good 선택 |
| D08 안전: filename query를 path로 바꿔 경고 | 올바른 no_supported_issue | 모두 good 선택 |
| J04 결함: 실제 count1을0으로 바꿔 미검출 | 올바른 결함 보고 | 모두 good 선택 |

critic은 완전한 판정 회복3/4, 쌍 비교는8/8이다. 쌍 비교가 보이는 소스와 모순되는 후보를 제외하는 기본 기능은 확인했지만, 단순하고 작성자가 구성한 모순에 대한 결과다. 복잡한 후보·불완전한 근거·둘 다 틀린 후보에 대한 선택 능력은 확인하지 않았다.

## 비용과 검증

| 최종 조건의 논리적 합산 | 호출 | provider 입력 tokens | 출력 tokens |
|---|---:|---:|---:|
| 기본 | 16 | 159,721 | 5,115 |
| 기본+critic | 32 | 325,695 | 9,815 |
| 기본+독립 후보+쌍 선택 | 48 | 488,473 | 12,073 |

기본 응답은 두 확장 조건에서 공유했다. 표의 호출/비용을 서로 더하면 중복 계산이므로 실제 물리적 합계와 구분해야 한다. 입력 tokens에는 Codex의 시스템 입력도 포함된다. cached 입력은 input의 일부다. 금액으로 환산하지 않았다.

본실험은64회 + 순서교환 감사4회=68회, 입력693,154(cached388,608), 출력17,123 tokens다. 추가 기능 진단12회는 입력144,337(cached77,568), 출력2,355 tokens다. 총80회 모두 transport/schema가 성공했고 관측된 도구 호출0, citation ID·status/list·ledger 이슈 관계 오류0이었다. protocol/source/prompt/schema의 실행 전 freeze 해시도 모두 일치했다. 채점·감사 후처리 스크립트는 실행 중 추가됐으며 source/witness 판정은 작성자가 arm을 보는 비맹검 방식이다. 단일 모델·단일 실행이고 사례 수가 작아 일반 성능 향상을 주장하지 않는다.

## 판단

**2번은 입력·분기 가정을 바로잡는 기능이 있지만, 판정 범위를 외부 시스템의 최종 결과까지 넓히면 불필요한 기권을 늘릴 수 있다. 3번은 후보가 실제로 다를 때 근거 있는 선택을 한 사례가 있지만, 기본 리뷰 대비 개선은 아직 없다.** 우선순위는 실제 실행 조건이 포함된 근거 확보를 유지하고, 추가 검토/선택은 기본 채택보다 오류·불일치 사례에서의 후속 검증에 둔다.

다음 성능 비교에는 기본 리뷰가 실제로 틀리거나 후보가 불일치하는 더 어려운 자연 사례, 독립 판정, 같은 호출 예산의 자체 재검토 대조군이 필요하다. 이번의 짧은 통제6쌍을 더 반복하는 것으로 그 공백이 해소되지는 않는다.

자료: 사전 protocol, 결과, 감사, 작성자 판정, 사후 기능 진단.
