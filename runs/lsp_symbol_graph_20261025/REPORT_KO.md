# SCIP 아이디어를 차용한 LSP 탐색 비교 결과

2026-10-25 · 동일 12개 Python PR · G0/H 각 72개 리뷰 · 신규 최종 모델 실행 144회

## 결론

**이번 H 구현에서는 F1 개선을 확인하지 못했다.** 기존 G 입력을 새로 평가한 G0의 엄격 F1은 **35.29%**, 심볼 관계·탐색 정책을 적용한 H는 **32.00%**로 **3.29%p 낮았다**. 엄격한 근거 기준으로 새롭게 탐지한 위치는 없고, G0가 탐지한 위치 하나를 H가 최종 보류했다. 국소 원인을 인정하는 local F1도 47.06%에서 44.00%로 낮았다.

H의 평균 공급 소스는 13.66% 줄었지만 정확도 이득으로 이어지지 않았다. 현재는 **기존 G를 유지하고, 관계 기반 후보 정렬부터 작은 개입으로 다시 분리해 검증하는 방향**이 적절하다. 이 결과를 SCIP 전체의 유효성에 대한 판정으로 확대하지 않는다. 이번 비교는 자체 구현한 복합 후속 탐색 정책의 결과다.

## 무엇을 비교했는가

- **G0**: 원래 G의 최종 source/plain 및 first 응답을 정확히 사용하고, 최종 모델 판단을 새로 생성했다. diff-only B0와 다른 대조군이다.
- **H**: 같은 초기 seed와 같은 first 응답에서 출발해 실제 LSP 정의·참조 결과를 심볼/등장 위치/관계로 구조화하고 후속 조회·후보 선택을 바꿨다. 최종 모델 판단도 새로 생성했다.
- 12 PR × 안전/결함 2방향 × 3반복 = 군당 72개다. 양군의 first는 동일한 원본 72개를 공유한다. 논리 first 슬롯 144개는 새 관측 144개가 아니다. 최종 신규 모델 실행만 총 144회다.
- 모델은 `gpt-5.6-sol`, reasoning `low`; prompt·schema·공개 계약·DIFF·소스 snapshot·채점 기준을 유지했다. 모델 직접 도구 사용은 0회다.
- 초기 소스 전체를 바이트 단위 prefix로 보존했다. source 5,200 reference tokens, static observation 800, 초기 native 최대 12 + 추가 6, query-origin 깊이 3, native 후보창 32, 조회당 신규 package 최대 4 제한을 유지했다.
- 실제 H 사례 탐색 전 정책·합성 테스트·채점·분석 코드를 봉인했고, 모델 실행 전 준비된 모든 입력을 다시 봉인했다. 평가 결과를 보고 정책을 수정하지 않았다.

따라서 추정 대상은 **공유된 첫 응답에 조건부인 후속 탐색·선택 묶음의 효과**다. 처음부터 새로 실행한 전체 agentic pipeline 효과는 아니다. 과거 G의 엄격 F1 **31.37%**는 역사적 참고값이다. 주 비교에 그 값을 사용하면 H 32.00%를 개선으로 오해할 수 있으므로, 동시 재평가한 G0 **35.29%**와 비교했다.

## 실제로 적용한 SCIP 아이디어

SCIP indexer나 protobuf를 설치하지 않았다. 공식 [scip.proto](https://github.com/scip-code/scip/blob/main/scip.proto)의 symbol/occurrence/relationship 구조화 아이디어를 기존 LSP 결과에 적용했다.

1. 실제 native 선언 위치와 원문 snapshot hash로 심볼을 구분하고, 여러 occurrence의 미확인 관계를 같은 실제 정의에 연결했다. 같은 이름만으로 다른 파일·버전을 합치지 않았다.
2. 호출·읽기·상속 등 관계 유형과 이미 공급한 코드 여부를 후보 선택에 사용했다. 기존 G의 missing-symbol 힌트는 유지했다.
3. Python protocol 사용에서 필요한 메서드, 명시적 annotation·대입·반환 annotation, native로 도달한 클래스의 직접 멤버·base expression을 후속 탐색 힌트로 사용했다.

3번과 후보 우선순위는 이 실험의 자체 설계다. **심볼 구조화, 후보 정렬, protocol 탐색의 개별 효과는 이번 두 군 비교로 분리하지 못한다.** 그래프는 내부 선택에만 사용하고 새로운 그래프 설명을 모델 prompt에 넣지 않았다. 정적 reference를 실제 runtime dispatch나 data flow의 증명으로 취급하지 않았다.

실제 72쌍에서 조회 순서는 모두 달라졌고, source는 66쌍, plain은 72쌍에서 달라졌다. 여러 occurrence가 연결된 canonical 심볼은 61쌍에서 152개로 집계됐다(반복을 합친 world별 중복 제거 57개). 그러나 canonical cached closure 재방문은 N08_b의 세 반복에서만 발생했고, 직접 결과는 모두 `already_supplied`였다. 이후 생성자 조회로 이어지는 간접 경로는 관찰·코드 순서로 추론할 수 있지만, 그 경로의 linked occurrence는 하나여서 **여러 occurrence 병합이 정확도를 높였다는 증거는 아니다**.

후보가 여러 개였던 115개 결과 중 실제 후보 순서가 달라진 것은 30개다. graph frontier로 실행한 235개 조회 중 새 번호줄 공급은 39건, class-member frontier의 31개 실제 조회 중 새 번호줄 공급은 17건이었다. 합성 Pyright 테스트 7개는 메커니즘 작동을 확인했지만, 실제 12개 사례의 엄격 TP 증가로 이어지지는 않았다.

- **N12_b_r3 — 엄격 탐지 손실.** G0는 empty-name guard 삭제와 생성자 종료까지의 실행을 보고했다. H는 같은 국소 원인을 설명했지만 public export 연결을 요구하며 최종 finding을 철회했다. 이 쌍의 실제 numbered source 줄 집합은 같다. G0에 더 있던 lexical inventory와 조회 요약 차이가 있으므로 완전히 같은 입력은 아니지만, H가 필수 생성자 코드 줄을 잃어서 실패했다고 설명할 근거도 없다. 한 쌍으로 문맥 차이와 모델 샘플링 효과를 분리할 수 없다.
- **N11 — Local 탐지가 반복 사이에서 교체됨.** r2에서 G0는 정확한 AST 원인을 보고하고 H는 보류했다. r1에서는 반대로 H가 보고했다. H가 Scanner.lex 본문을 새로 공급한 것은 사실이나 Expression.compile 진입점 연결은 여전히 없었다. 군별 Local TP는 각각 1개로 같고 strict TP는 모두 0개다.
- **N02 — 기존 성공 유지.** 두 군 모두 CharField(Field)와 직접 선언 inventory, Field.__deepcopy__ 본문으로 상속 복사 연결을 보완해 세 반복 모두 탐지했다. H가 덜 가져온 CharField.__init__ 본문은 해당 좁은 복사 증명의 필수 근거가 아니었다.
- **N05 — 새로운 검색의 공로로 세지 않음.** 두 군 모두 세 반복에서 정확한 독립 Decimal 입력의 prec=0 원인을 보고했다. 결정적 산술과 본문은 초기 seed에 이미 있었다. 첫 응답 보류→최종 탐지 전이를 모두 H의 신규 검색 발견으로 귀속하지 않았다.
- **N03 — 원인 추론 오류 지속.** 두 군 모두 결함 방향 세 반복에서 functools.wraps 자체가 실패한다고 잘못 설명했다. 실제 user wrapper의 f.__name__ 접근과 구분해야 하며, 관계 탐색만으로 이 오류가 고쳐지지 않았다.

H 준비는 2개 native worker로 135.88초, 최종 모델 실행은 최대 2개 병렬로 1,078.44초(17.97분)였다. 실제 CLI 시작 간격은 최소 3.009초였다. 전체 144개 raw/trajectory가 정상이며 실행기 재시도와 resource circuit은 0회다. G0는 과거 native 결과를 재사용했으므로 두 군의 native wall time을 공정한 속도 비교로 해석하지 않는다. 관측되지 않은 HTTP 내부 시도 횟수는 주장하지 않는다.

## 다음 실험의 우선순위

1. **기존 G의 조회·근거 선택을 유지한 채 native 반환 후보의 관계 기반 정렬만 분리한다.** 이번 H는 모든 위치의 조회 순서를 바꾸고 여러 탐색 휴리스틱을 함께 적용해 개별 효과를 판별하기 어려웠다.
2. **protocol 탐색은 별도 제한된 예산으로 검증한다.** 기존 필수 연결 조회를 밀어내지 않도록 범위를 줄이고, 메서드 하나의 추가보다 진입점→실패 지점의 필요한 연결을 끝내는지를 측정한다. 이번 비교에서 효과가 검증된 설정이라고 주장하지 않는다.
3. **같은 코드에서 판단이 바뀐 원인은 source 선택과 plain 조회 요약을 분리해 확인한다.** 현재 source가 같은 경우에도 plain은 모두 달라져 순수한 동일 입력 반복 대조가 아니다. 이 분리는 근거 기준을 느슨하게 만드는 방식으로 하지 않는다.

위 제안은 다음 실험 후보이며 이번 실행 중 정책 변경이나 추가 실행을 하지 않았다. 이후 개선을 주장하려면 새 holdout PR와 독립 채점, 다른 언어로 확인해야 한다.
