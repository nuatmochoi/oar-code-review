# 실제 LSP와 AST 기반 코드 리뷰 비교 — 2026-10-01

실제 Pyright 언어 서버를 연결해 비교를 완료했다. LSP는 재수출된 클래스의 정의를 찾아 구조적 대조 사례에서 한 쌍을 더 맞혔다. 기존 회귀 사례에서는 엄격한 근거 기준으로 성능 개선이 없었다. 따라서 **LSP 정의 탐색의 효과는 관찰했지만, 코드 리뷰 전반의 우월성을 입증한 결과는 아니다.**

## 비교 조건

- AST: 기존의 제한된 이름·factory·alias·호출 인자 binding 해석기. 일반적인 모든 AST 분석 기법을 대표하지 않는다.
- LSP: Pyright 1.1.414, 실제 stdio JSON-RPC의 `initialize`, `didOpen`, `textDocument/definition`. 정의 탐색 실패 시 AST로 대체하지 않는다.
- 양쪽에 동일한 저장소 소스, 문법상 질의 위치, 질의 순서·최대12회·깊이3, BM25 prefix800, 소스1600 reference tokens, 질의 관측400 reference tokens를 적용했다. 모델 입력에는 호출 위치→정의 후보 관계와 미해결 관측도 같은 형식으로 제공했다.
- 모델은 `gpt-5.6-sol`, reasoning effort low. 동일 리뷰 프롬프트·응답 스키마·사실 확인 ledger, 모델 도구 사용0, 재시도 없음. LSP는 모델 호출 전에 실행된다.
- 19쌍 × 안전/결함 버전 = 38개 world, 양 arm 합계76개 논리 리뷰. 최종 입력이 동일한26개 world는 같은 실제 응답을 공유했다. 나머지는 별도 호출해 **실제 모델 호출50회**를 완료했다. 입력이 같은 두 응답을 독립 표본으로 해석하지 않는다.
- 소스만 제공하던 준비안에 질의 관측을 추가한 시점은 모델 호출0회였다. 이전 준비 freeze를 별도 보존했으며 최종 입력·코드·라벨·정책을 호출 전에 다시 고정했다. 이전 실험과 공통 질의 정책이 달라졌으므로 이전 점수와 직접 전후 비교하지 않는다.

## 결과

정답 쌍은 결함 버전에서 근거 있는 결함을 찾고, 안전 버전에서도 근거 있는 무결함 판정을 한 경우다. 기권, 근거 없는 경고, 근거 없는 안전 단정은 정답으로 처리하지 않았다. 실패·기권을 분모에서 제외하지 않았다.

| 평가 | AST | 실제 LSP |
|---|---:|---:|
| 정의 해석 기능 확인: 기대 정적 후보 집합과 일치 | 3/10 | 10/10 |
| 공통424회 질의 중 저장소 내 함수·클래스 후보 확보 | 112/424 | 130/424 |
| 기존 회귀14쌍: 근거 있는 결함 검출 | 11/14 | 11/14 |
| 기존 회귀14쌍: 양쪽 버전 모두 정답 | 11/14 | 11/14 |
| PNG 경로 명시 진단1쌍: 양쪽 버전 모두 정답 | 0/1 | 0/1 |
| 구조적 대조4쌍: 근거 있는 결함 검출 | 2/4 | 3/4 |
| 구조적 대조4쌍: 양쪽 버전 모두 정답 | 2/4 | 3/4 |
| 안전 버전19개에서 보고된 결함 오탐 | 0/19 | 0/19 |

10개 기능 확인 사례는 직접 호출, 타입 지정 인자, 상속, 재수출, property, 반환 타입, 미지의 인자, union, shadowing, UTF-16 위치 처리다. 기대 후보가 비어 있는 두 사례도 포함한다. 선택한 기능 사례의 일치율이며 실제 리뷰 정확도가 아니다. 타입 표기와 union 후보는 실행 시 receiver 확정을 보장하지 않는다.

### LSP가 실제로 도움이 된 사례

W03에서 `public_api.ReviewService`라는 재수출 이름을 `StringLength`로 연결했다. 결함 버전은 `' abc '` 길이를 `len(string)` 대신 `len(string.strip())`로 계산해5→3으로 바꾼다. AST는 재수출 연결 근거가 부족해 기권했고, LSP는 정적 정의 관측과 전달된 본문·인자로 결함을 검출했다. 안전 버전은 양쪽 모두 맞혔다.

W01 조건부 factory와 W02 상속은 양 arm 모두 맞혔다. 기존 BM25 소스에도 필요한 factory 본문이나 상속 헤더가 보였기 때문에 LSP만의 추가 이득은 없었다. 모델에 전달된 소스 본문이 달라진 world는4개, 질의 관측까지 포함해 최종 입력이 달라진 world는12개다.

### 정답으로 인정하지 않은 출력

- **F03 LSP 결함 경고:** 빈 ORM 질의가 거짓으로 평가되어 helper가 None을 반환한다고 가정했다. 확보한 정의는 해당 ORM 실행 의미를 증명하지 않는다. 기존 AST의 기권보다 좋은 검출로 계산하지 않았다.
- **F08 양 arm 결함 경고:** request.path와 IMG_EXTENSIONS가 미확인인데 이미지 확장자 분기가 실행되고 max-age=3600이 된다고 단정했다. 근거 없는 경고로 처리했다. 경로를 `/generated.png`로 명시한 P08도 전역 상수들이 입력에 빠져 양 arm 모두 결함 버전에서 기권했다.
- **W04 LSP 안전 판정:** property 반환 타입을 바탕으로 정적 후보를 찾았지만 getter 본문은 모델 입력에 없었다. 실제 receiver가 해당 구현을 호출한다는 안전 판정의 ledger 근거를 인정하지 않았다. 결함 오탐은 아니지만 정답 안전 판정도 아니다. 결함 버전에서는 양쪽 모두 기권했다.

기존 회귀의 근거 없는 결함 경고는 AST1개, LSP2개다. 기권 수는4→3으로 줄었지만 그 감소를 성능 향상으로 해석하면 안 된다. 구조 대조에서는 전체8개 world 정답이5→6이고, LSP의 W04 안전 단정1개는 제외했다. W03의 binding 설명은 입력의 E-NAV 관측으로 뒷받침되지만 응답의 인용 목록에 해당 E-NAV가 빠졌다. 입력 근거 부재와 구분해 인용 완전성의 한계로 기록했다.

## 실행·감사

주 실험에서 실제 `textDocument/definition` 요청424회를 보냈고 서버 오류는0회다. 같은 코드 위치를 여러 world에서 조회한 요청을 포함하므로424개의 서로 다른 심볼이라는 뜻은 아니다.

- Native 응답에 위치가 있는 요청332회, 빈 응답92회.
- 그중 공통 소스 추출 정책이 받는 저장소 내 함수·클래스 후보130회.
- Native 위치를 받았지만 외부 파일·변수·미색인 위치 등으로 필터링한 요청202회. 이를 LSP 호출 실패로 부르지 않는다. 반환 위치 수와 요청 수는 구분한다.
- 정의 조회 대기 시간 합계7.49초,38개 workspace의 서버 시작 시간 합계4.26초. 모델·준비 시간은 제외한 값이며 AST 대비 속도 개선 주장은 하지 않는다.
- 실제 모델50회 모두 transport·스키마·인용 ID 감사 통과. 실제 사용량: 입력579,972 tokens, 그중 cached363,904, 출력21,906. AST38회와 추가 LSP12회의 물리 호출 합계이며 LSP 전체 arm 비용과 같지 않다.
- 구조 대조4쌍에서 실제 execute 함수 본문을 base/head 각각 두 번 실행해32개 결과를 확보했다. NodeOutput은 tuple 전달 경계로 대체했으며 wrapper/framework 전체를 실행한 테스트가 아니다. 기존 사례의 witness는 이전 기록을 참조했다.
- 호출 전 파일 해시, staging 소스·설정 동일성, 이전 corpus 동일성, 컨텍스트 한도, 공유 입력 동일성, 라벨·채점 집계 검증을 통과했다. 모델을 재호출하지 않고 저장된 결과를 검증했다.

## 해석과 다음 단계

이번 비교는 **실제 LSP를 사용한 컨텍스트 탐색 backend 실험**이다. 질의는 고정된 문법 기반 순서로 미리 실행했다. 모델이 issue에 맞춰 jump를 선택하거나 RL로 학습하는 RepoNavigator 전체 재현은 아니다. 논문의 목적도 repository navigation이며 리뷰 적용은 여기서 설계한 확장이다. [ICML 공식 논문](https://proceedings.mlr.press/v306/zhang26an.html), [논문 본문](https://arxiv.org/html/2512.20957v6).

14쌍은 기존 선언 입력 기반 회귀 자료이고, 추가4쌍은 같은 저장소에서 만든 구조 대조다. 독립적인 자연 PR holdout, 블라인드 채점, 여러 seed 반복은 아니다. 작성자가 소스와 witness를 보고 채점했다. 단일 모델 호출의 변동성도 분리하지 못한다.

또한 전체 운영 의존성을 설치한 환경이 아니다. 정적 분석 설정·Python3.11·저장소 경로를 고정했고 외부/비호출 심볼은 소스 추출 정책에서 제외했다. **LSP의 기능이 좋아도 getter·전역 상수·실제 DB 의미가 컨텍스트에 없으면 리뷰 근거가 닫히지 않는다.**

다음 우선순위는 property receiver의 getter 본문, 전역 상수·설정 심볼을 함께 조회·추출하도록 양 arm의 공통 정책을 확장하는 것이다. 그 뒤 같은 예산에서 다시 비교하고, 새로운 저장소의 자연 PR과 여러 반복으로 검증해야 한다. 현재 결과는 LSP 유지 근거는 되지만 전면적인 리뷰 성능 개선 근거는 부족하다.

## 재현 파일

- `PROTOCOL_KO.md`, `freeze.json`: 호출 전 고정 조건·해시·공유 매핑.
- `lsp_client.py`, `backend.py`, `lsp_traces/`: 실제 LSP 연결·질의·응답.
- `resolver_tests.json`, `witnesses.json`: 정적 후보 확인 및 함수 본문 실행 결과.
- `inputs/`, `raw/`: 물리 호출50회의 실제 입력·응답. 공유 LSP 응답을 별도 원시 호출처럼 복제하지 않았다.
- `audit.json`, `navigation_summary.json`: 운영·출처·질의 결과 감사.
- `annotations.json`, `adjudicate.py`, `results.json`, `score.py`: 수동 판정 이유 및 점수. `python3 score.py`로 집계 재생성 가능.
- `validation.json`, `validate_results.py`, `result_seal.json`: 결과 무결성 확인 및 사후 해시.
