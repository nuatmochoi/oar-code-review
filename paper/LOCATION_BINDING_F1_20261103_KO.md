## 판정

**이번 사례에서는 HEAD 번호 명시를 우선 채택할 근거가 있고, AST 연산 ID를 기본 방식으로 추가 채택할 근거는 부족하다.** 주 비교인 연산 ID−행 ID의 표시 anchor 오류율 차이는 Python/Go·diff/본문 문맥의4개 셀 모두0이었다. 양쪽 모두 원인 내용이 맞는 paired subset에서도 위치 승/패는 모두0/0이다(Go diff14·본문18, Python diff14·본문18 보고). 기존 행 ID부터 위치 오류가0인 표본이라 추가 이득을 확인하지 못했다.

Python diff-only에서는 기존 자유 인용의 내용 정탐13건 중 위치 오류2건이 HEAD 번호 표시 조건에서0건으로 줄었다. 두 조건 모두 내용이 맞는12개 paired 보고에서도 번호 표시의 위치 승2·패0이었다. 두 오류는 Rational 사례의 정상 분자 변환1629행과 빈1627행을 지목한 경우다. 번호 표시 조건은 실제 문자열 반복 연산1630행을 선택했다. 이 후속 교집합 진단은 처치 후 선택 효과가 있어 전체 지표의 대체 증거로 쓰지 않는다.

유효 원인F1은 Python diff에서64.71→80.00→80.00→83.33%, 본문 제공에서는88.89→100→100→100%였다. Go diff는88.24→90.91→94.12→88.24%, 본문 제공은86.49→94.44→100→100%였다. 순서는 기존 자유 인용→HEAD 번호→행 ID→AST 연산 ID다. AST 조건은 diff에서 Python +3.33pp·Go −5.88pp로 방향이 다르고, 본문 제공에서는 두 언어 모두 동률이었다. 이 차이는 위치 정탐 증가가 아니라 원인 내용 정탐·오원인·미탐 차이에서 나왔다.

본문 제공 문맥의 자유 인용에는 Python2·Go2건의 ID/범위 손실이 남았다. Go 번호 표시에도1건이 남았고, 두 controller 조건에서는 이 기계적 손실이 없었다. Controller의 인용 결속은 안정화에 유용하지만 이것이 AST 연산 표현의 독립적인 추가 효과라는 뜻은 아니다. 서로 다른 prompt/schema로 새 응답을 생성한 조건 간 관찰이며 기존 raw 답변을 사후 고쳐 점수를 올리지 않았다.

여기의100%는 고정한 국소 target 원인 기준이며 설명 전체가 무오류라는 뜻은 아니다. 실제 `f.__name__` 실패를 맞히면서 wrapper 자체에도 이름이 없다고 덧붙이거나, 실제 `len(a)=0`을 맞히면서 iterator까지 비어 있다고 잘못 설명한 부수 오류는 원래 판독 이유에 보존했다. 이런 오류까지 모든 원인 주장별로 검증하는 것은 후속 실험의 별도 평가 과제다.

단일행 anchor와 실제 연산 관련성을 분리한 결과, 내용 정탐인 operation 보고의 선택 node는 모두 관련성이 있었다. 그러나 이 진단은 내용 정탐에 조건화되어 있다. diff-only Django에서는4개 형식 모두3반복 내내 `wraps/update_wrapper`가 예외를 낸다는 오원인이 남았다. 실제 partial 연산 ID를 정확히 선택해도 그 API 동작 가정은 틀렸다. 반대로 실제 stdlib 본문이 있는 문맥에서는4개 형식 모두 실제 사용자 wrapper의 `f.__name__` 실패를 설명했다. 문맥 조건은 여러 본문을 함께 바꾸므로 이를 외부 구현 연결 하나만의 순수 효과로 해석하지 않는다.

AST 연산 형식의 provider 입력은 행 ID 대비 Python diff7.76%·본문13.89%, Go diff5.50%·본문10.42% 증가했다. 후보 종류·코드 반복·후보 수가 함께 바뀌고 cache 사용량도 달라 실제 요금 증가율과 같지는 않다. 공통 의미 정답에서 위치 이득이0인 점을 고려하면 현재 표본에서 이 추가 입력을 정당화할 성능 근거는 얻지 못했다.

576개 결과·입력·수동 채점, 물리 시도576회가 모두 완결됐다. 전송/출력 실패0, wrapper 재시도0이며 provider 사용량 미상 시도도0이다. 입력8,175,042·출력183,798tokens를 보고했다. cache 입력2,878,464는 입력의, reasoning 출력73,255는 출력의 부분집합이므로 더하지 않는다. 비용에는 협업 평가 모델과 미계측 내부 I/O가 포함되지 않는다.

N02의 DIFF202는 삭제된 BASE202 dictionary copy를 참조하며, 리뷰 표시 HEAD202는 별도의 pure-deletion 경계다. BASE 근거/HEAD anchor 독립 검토. 관련 범위의1행 overhang만으로 탈락시키는 새 gate는 없다. pure-deletion HEAD 경계 예외도 모든 형식에 동일 적용하고, 단순히 근처 행이라는 이유만으로 무관한 연산을 구제하지 않았다.

## 7. CuraLoc·ARISE와 비교한 연구 판단

사용자가 첨부한 검토의 중심 판단에 동의한다. CuraLoc은 symbol과 탐색 관계를 계획해 결정론적으로 소스를 수집하고 SID·AST metadata로 출력을 연결한다. 실패에 관여한 코드와 수정해야 할 코드가 다를 수 있다는 관점도 이미 명시한다. 따라서 계획적 탐색·관계 활용·짧은 ID나 두 위치의 구분 자체를 새 기여로 주장하기 어렵다. [CuraLoc v2 §1·§3·Appendix A](https://arxiv.org/html/2610.31809v2).

ARISE는 Python 함수 내 문장 단위 def-use slicing을 도구로 노출하고, 동일 schema에서 문장/dataflow 정보를 없앤 Coarse 대조도 둔다. 주요 line 정답은 패치가 건드린 행이며 별도의 실제 실패 연산 annotation이 아니다. AST 세분화나 schema/정보 효과 분리만으로는 차별화가 약하다. [ARISE v2 §3](https://arxiv.org/html/2605.03117v2).

가장 유망한 기여 후보는 “외부 구현·소비 경로의 누락으로 잘못 가정한 API 동작을 찾고, 실제 근거와 대조해 오원인을 교정한다”는 방향이다. stdlib 본문을 가져온 사실만으로 새롭다고 할 수는 없다. 어떤 가정이 왜 틀렸고 어떤 본문이 그 가정을 반박했는지를 미사용 PR에서 반복 검증해야 한다. version/origin hash는 읽은 출처를 확인하지만 해당 PR의 lock 버전·실제로 호출되는 구현 일치까지 보장하지 않는다.

현재 수집기는 본문 우선 수집 정책이고 catalog/controller는 실제 코드 존재와 좌표를 확인한다. 가설별 반증·재탐색이나 설명–실제 실패 연산의 자동 의미 검증까지 구현했다고 할 수 없다. 이번 위치 비교는 기반 안정화다. 원인 설명에 맞는 정확한 AST 연산인지에 대한 판독 역시 수동 보조 진단이다.

후속 논문 검증은 동일 후보 symbol·최종 reviewer에서 선언/stub 대 실제 외부 구현, 동일 구현에서 소비자 본문 유무, 동일 public input·도구·source pool·총예산에서 CuraLoc식 선택 adaptation 대 현재 선택을 비교하는 것이 우선이다. adaptation을 원논문 그대로 실행한 baseline처럼 표기하지 않는다. ARISE와는 패치 행 회수와 실제 실패 연산 이해를 구분한 평가가 필요하다.

현재 공개 계약은 구체 입력·기대 결과를 줘 일반 PR 리뷰보다 강한 단서다. 같은12개 개발 사례의 높은 점수는 그 조건부 개발 증거이며 일반 코드리뷰 효과를 보장하지 않는다. 관련 연구 두 편에 그 평가가 중심으로 없다는 것도 전체 문헌에서 신규라는 증명은 아니다.
