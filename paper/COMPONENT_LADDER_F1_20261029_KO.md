각 행은 바로 위 행의 입력을 포함한다. 2행은 Python AST로 선택한 변경 함수의 전후 본문·둘러싼 클래스/함수의 헤더·사용 import다. 3행은 실제 Pyright LSP의 정의·참조 조회와 선택된 완전 본문을 추가한다. 4행은 3행과 동일한 초기 근거에서 시작해, 첫 리뷰 이후 제품이 감지한 선언·관찰 근거의 부족과 모델 요청에 따라 코드를 더 조회한다.

여기서 추가 탐색은 grep/줄 읽기/심볼·호출 관련 도구를 사용하는 기존 제품의 후속 탐색 흐름이다. 이전 실험의 조회 우선순위 조정, 후보 상태 원장, controller 근거 기록, 자동 본문 보완은 넣지 않았다. 따라서 모호한 약어 하나로 여러 기능을 묶지 않는다.

원인 F1은 결함의 국소 원인을 정확히 보고했는지, 근거 F1은 그 원인에 필요한 사전 지정 코드 연결까지 실제 공급된 자료로 입증했는지 평가한다. 둘 다 유효한 최종 finding이 필요하다. 단순한 파일·심볼 위치 반환을 본문 근거로 간주하지 않는다.

`F1 = 2TP / (2TP + FP + FN)`, `FP = 마지막 응답의 보고 수 − TP`, `FN = 12 − TP`. F1은 precision과 recall의 조화평균이다. 근거 평가에서는 맞는 원인이라도 필수 코드 연결이 부족하면 TP에 포함하지 않는다. 안전 방향의 오경고 비율은 별도 열이다.

- **리뷰 후 추가 탐색:** `srepr`의 원인 경고를 회복했지만 근거 충족 정탐은 늘지 않았다. 결국 함수 문맥 조건과 같은 두 F1에 모델 호출은 24→34회가 됐다. 이번 개발 평가에서는 이 추가 비용으로 성능 이득을 확인하지 못했다.
- **다음 개선 가설:** 조회 수를 늘리는 것보다, 원인 가설에서 빠진 소비 함수·타입 구성·호출 연결을 특정해 해당 본문을 확보하는 정책을 검증할 가치가 있다. 예를 들어 Point 사례의 관련 호출자나 Printer 초기화 본문은 실제 필요한 Point 구성/순회 및 Symbol 출력 본문을 대신하지 못했다. 이는 다음 실험 제안이며 이번 결과에 반영한 기능이 아니다.

## 해석 범위

동일한 12개 Python 개발 사례를 반복 사용한 평가이고, 조건당 1반복이며 비맹검 AI 채점이다. 독립 인간 검증·새 hold-out·다른 언어의 성능 증거는 아니다. 모든 사전 지정 비교의 95% 구간은 0을 포함하므로 일반적인 우월성을 확정하지 않는다. LSP 단계는 관련 코드 범위와 본문을 추가하는 효과를 포함하므로 LSP 프로토콜만의 효과라고 해석할 수 없다. 추가 탐색은 재판단 횟수도 증가한다. 논문 또는 제품 채택 판단에는 새 사례와 반복 검증이 필요하다.

검증: 실행 전 테스트82개와 제품 흐름 모의 리뷰8개 통과. 실제 리뷰96개·모델 호출106회 정상, 직접 모델 도구 호출0, 예산·초기 근거 동일성·스키마·결과 해시 감사 오류/경고0. 이전 결과13,040파일, 고정 workspace 소스15,342파일, 원본 및 각 제품 snapshot149파일의 보존을 확인했다. 비용 표는 리뷰 호출의 provider 사용량이며 설계·채점 작업 비용은 포함하지 않는다.
