# Python·Go 문맥 단계 비교: 원인 F1·오탐·비용과 병목

2026-11-02 · 실제 변경 12개(Python 6·Go 6) · 결함/수정 양방향 · 5조건 · 새 최종 판단 3반복 · **360/360개 판단·채점 완료**

**이번 자료에서는 “Python이라서 추가 탐색 효과가 작았다”는 설명을 뒷받침하지 못했다.** Go도 AST에서 이미 결함 방향 판단 18/18건(6개 사례×3반복)을 맞혔고 LSP·추가 탐색의 신규 원인 정탐은 0건이었다. Python은 필요한 본문을 직접 제공하면 원인 F1이 100.00이 됐지만, 자동 추가 탐색은 LSP 대비 88.89→78.95로 하락했다. 자동 탐색의 필요한 본문 선택, 외부 API 구현 확보, 잘못된 안전 경고와 인용 생성이 남은 병목이다. 직접 제공은 정답 경계를 아는 연구자가 소스를 고른 진단 조건이므로 자동 방법의 달성 성능으로 채택하지 않는다.

## 1. 원인 F1·재현율·오탐·모델 비용

원인 TP는 정확한 결함의 trigger·실패 연산·영향을 유효한 최종 finding으로 보고한 경우다. 결함 방향당 최대 1TP, `FP=원시 finding 수−TP`, `FN=18−TP`, `F1=2TP/(보고 수+18)`이다. **원인 FP에는 틀린 원인·무효 인용/위치도 포함되므로, 안전한 코드에 경고한 리뷰 수와 다르다.** 중간 reasoning의 정답이나 올바른 관찰을 최종 finding으로 승격하지 않았다.

모델 전송·출력 실패 0, 재시도 0, 리뷰 모델의 도구 호출 0, usage 미상 0이다. 명시적 전체 판단 보류는 Python diff 1개, Go diff 8개·AST 4개·LSP 2개였으며 나머지는 0이다. 보류도 원래 분모에 남겼다. 수정 방향의 무경고를 저장소 전체 안전성 입증으로 해석하지 않는다.

## 3. 무엇이 빠졌고, 무엇을 주면 달라졌나

**N03는 외부 API 의미를 확인할 본문의 효과가 가장 분명했다.** diff/AST는 모두 `functools.wraps`의 metadata 복사가 예외를 낸다고 잘못 설명했다. 실제 `update_wrapper`는 없는 속성을 건너뛰고, 이후 사용자 wrapper가 captured partial의 `f.__name__`을 직접 읽을 때 실패한다. 직접 제공 조건은 실제 CPython 3.11.13의 `wraps/update_wrapper`와 Django 경로를 받아 세 번 모두 이 차이를 정확히 설명했다. LSP·추가 탐색은 각각 한 번만 정확했다. 새로운 언어 서버 위치보다 **필요한 API 구현 본문**의 부재가 이 사례의 구체적 병목이다.

**N10의 추가 탐색은 안전 방향에서 2/3회 오경고했다.** 두 응답은 두 Point 호출이 같은 런타임 타입이라고 가정해 새 padding guard가 실행되지 않는다고 주장했다. 실제 factory는 Point2D/Point3D를 생성한다. 검색 본문에는 이 factory 연결이 빠졌고 직접 제공에는 포함됐다. 또 설령 같은 타입을 가정해도 해당 fallback은 BASE에도 있어, 새로 도입된 결함인지 확인해야 했다. 따라서 실패를 오직 본문 부족 하나로 환원하지 않고 **미확인 타입 바인딩과 BASE→HEAD 회귀 확인 실패**로 함께 기록한다. LSP·직접 제공의 안전 방향은 모두 무경고였다.

**Go에서도 후보 선택이 핵심 호출을 놓쳤다.** GO02 추가 탐색은 `toLSPDiagnostic`은 읽었으나 `ToLSPRange/PositionToLineAndCharacter` 구현을 읽지 못했고, GO03는 `MkdirTemp/RemoveAll/OpenRoot/Close`에서 확장하느라 핵심 `OpenFile/createLink`가 빠졌다. 깊이 3·함수별 첫 후보 4개라는 선택 정책의 한계다. 남은 토큰이 있어도 후보에 없으면 읽지 못한다. Go의 정적 연결만으로 이 문제가 자동 해결되지는 않았다. 이번에는 국소 원인을 이미 맞혀 새 TP 증가로 이어지지 않았다는 점도 구분한다.

### 본문 확보와 정탐은 다른 지표다

동일하게 동결한 사례별 본문 단위 목록을 실제 최종 입력의 소스 블록 **및 diff의 HEAD 행**과 대조했다. 단위 전체가 공급된 경우를 센다. 이 목록은 필요한 연결을 덮도록 사전 선정한 운영 카탈로그이며, 수학적으로 최소인 증명 집합이나 모든 단위가 항상 의미적으로 필수라는 뜻은 아니다. 예를 들어 N09는 전체 Rational 생성자로 좁은 원인을 입증할 수 있어, Integer 생성자까지 받지 않아도 사전 좁은 근거 기준을 충족할 수 있다.

| 언어 | diff | AST | LSP | 추가 탐색 | 직접 제공 |
|---|---:|---:|---:|---:|---:|
| Python | 0/76 (0.00%) | 14/76 (18.42%) | 18/76 (23.68%) | 36/76 (47.37%) | 76/76 (100.00%) |
| Go | 2/78 (2.56%) | 14/78 (17.95%) | 20/78 (25.64%) | 29/78 (37.18%) | 78/78 (100.00%) |

Python은 LSP→추가 탐색에서 단위 확보가 18→36개로 늘었으나 원인 F1은 하락했다. **본문 수 증가를 성능 증가로 대체할 수 없다.** Go도 AST부터 원인 F1 100이므로 전체 카탈로그 완성을 결함 경고의 필수 게이트로 삼으면 맞는 국소 원인까지 억제할 수 있다.

diff의 전체 단위 완성률이 작아도 코드가 없는 것은 아니다. 실제 diff에는 Python 사전 단위의 유효 코드 행 88/850, Go 101/1,197이 있었다. 원래 source audit의 “추가 소스 블록만” 지표와 구분해, 후속 실제 입력 감사에서 diff 행을 합쳤다. 입력 360개에서 실제 전달을 확인했다. 이 확보율은 원인 재현율·근거 F1·런타임 경로 증명과 동일하지 않다.

## 4. 원인은 맞아도 유효 보고가 되지 못한 사례

| 보고 | 유효 TP에서 제외한 이유 | 해석 |
|---|---|---|
| PY_N05_a_search_r2 | BASE source ID 마지막 문자를 누락 | 원인 내용은 정확하지만 인용 ID가 존재하지 않음 |
| PY_N09_a_diff_r2 | 최종 finding 위치가 실제 연산이 아닌 빈 줄 1627 | 문자열 분모 반복 원인은 정확하지만 위치 무효 |
| GO05_a_oracle_r3 | Context 선언 ID(16–34행)에 newContext 범위(139–145행)를 결합 | 필요한 코드와 정확한 설명이 있었지만 인용 결속 실패 |

이 세 건은 원시 응답을 고치거나 좋은 답변으로 재실행하지 않았고, 주 F1에서 FP/FN으로 남겼다. 특히 Go 직접 제공의 94.44는 source 부족/원인 오해가 아니라 이 마지막 보고 유효성 오류 1건에서 발생한다. 모델의 의미 판단과 controller의 ID·범위 생성 책임을 분리할 후속 근거다. 현 실험에서 인용을 자동 보정한 방법의 효과를 측정했다고 주장하지 않는다.

GO05_a_search_r3의 위치 판정은 별도 독립 재검토했다. 삭제된 요청별 복사와 연결되는 실제 Logger 덮어쓰기 71–75행은 변경된 ServeHTTP 안의 유효한 실패 연산 위치다. 원래 계획에 없던 “추가된 행에만 정탐 허용” 규칙을 적용하지 않아 cause TP 1로 판정했고, 초기 0 판정 원본·해시와 변경 사유를 모두 보존했다. 해당 한 건만 다시 제외하는 민감도에서는 Go 추가 탐색 F1이 94.44가 되어 LSP 대비 이득이 사라진다. 따라서 작은 Go 차이를 견고한 우위로 포장하지 않는다.

또한 PY_N07_a_diff_r2와 AST_r3는 실제 길이 0이라는 핵심 결함을 정확히 보고해 원인 TP로 인정했지만, “iterator도 0개를 낸다”는 부가 설명은 틀렸다. 실제 iterator는 1개를 낸다. 정탐이 모든 설명 문장의 무오류를 보장하지 않는다는 한계도 기록했다.

## 5. 실제 비용과 병렬 실행

- 실제 신규 모델 판단·물리 시도 **360회**, 재시도·실패 **0회**. 입력 **4,109,980**, 출력 **111,479** 토큰.
- 캐시 입력 2,812,160, reasoning 출력 36,730 토큰은 각각 위 총량의 부분집합이므로 다시 더하지 않는다.
- 최대 동시 4개, 시작 간격 최소 3초. 전송·시도별 usage·프로세스 회수와 실제 입력/결과 해시를 감사했다. 모델 실행 시간은 gate/attempt 기록으로 별도 보존했으며, 수집·구현·채점까지 포함한 전체 연구 시간을 모델 latency로 표시하지 않는다.
- 같은 HEAD+BASE 소스 합집합 상한 5,200 reference tokens를 썼다. 이는 실제 provider 입력 토큰, 동일 실제 계산량, 같은 현금 비용을 뜻하지 않는다.

수집은 방향당 한 번 수행해 3개 모델 반복이 공유했다. LSP 초기 수집은 추가 탐색 조건과 공유하므로 표의 누적 LSP/search 비용을 물리 합계로 더하거나 3반복만큼 다시 곱하지 않는다. 시간 합계는 개별 작업 시간의 합이며 병렬 wall time과 다르다. Go CLI 내부 wire RPC 수와 전체 파일 I/O는 미계측이다. 기록의 body_reads는 언어별 부분적인 논리 읽기/편입 블록 계수라 전체 물리 I/O 비용으로 비교하지 않았다.

Go native 238회 중 4회는 GO01 양방향에서 외부 fmt/slices 해석 중 발생한 workspace/view 오류였다. 타임아웃은 0이다. Python 본 수집의 native 실패는 0이다. 이 오류는 모델 호출 실패도, Python/Go의 본질적인 언어 차이도 아니다. stderr와 실패 비용을 보존했다.

표의 Python 559회는 최종 본수집이다. 본문 번호가 중복되는 초기 schema 문제를 발견한 N05_a 준비 진단에서도 별도 native 40회(모델 0회)를 사용했다. 이 시행착오 기록은 `python_context/superseded_preflight_v0`에 보존했으며 559회에 포함하지 않았다. 전체 연구 준비 비용을 최종 본수집 수치만으로 대표하지 않는다.

추가 탐색의 실제 모델 입력은 LSP 대비 Python 약 36.79%, Go 약 25.59% 증가했다. 직접 제공의 읽기 시간은 연구자가 정답 경계를 보고 소스를 선정한 수작업 시간을 포함하지 않으므로 자동 검색 비용의 대안으로 비교하지 않는다. 설계·초기 스모크·독립 witness·협업 AI 채점 비용도 위 본실험 모델 토큰 합계에 포함하지 않았다. 가격을 가정해 현금 비용으로 환산하지 않았다.

## 6. 비교 조건과 해석 한계

모든 조건은 gpt-5.6-sol/low, 동일 공개 계약·diff·최종 응답 schema, 최종 판단 1회다. verifier/debate·초기 리뷰 응답·후속 재판단은 없다. 추가 탐색은 실제 공급 코드의 호출·상속 등에서 결정적으로 확장한 source-only 정책이며, 기존 프로젝트의 모델 요청형 agentic 탐색 전체를 재현한 조건이 아니다. 모든 native 조회는 이번에 새로 수행했고, 과거 모델 점수를 대조군에 섞지 않았다.

- Python은 기존 개발 PR N02/N03/N05/N07/N09/N10을 다시 사용했다. Go는 실제 PR head의 목표 결함과 연구자가 만든 좁은 수정 대조군을 비교했다. 수정 방향은 해당 공개 계약의 목표 결함에 대해서만 안전하며, 저장소 전체 안전성을 의미하지 않는다.
- Go 대상은 GoFr 1355/1681/1696, TypeScript-Go 1000, Ollama 9379, WaveTerm 1793의 실제 소스다. 원 데이터의 NATS 후보는 설명과 실제 초기화 경로가 맞지 않아 **첫 모델 실행 전에 제외**했으며 원본 초안과 제외 근거를 보존했다.
- Go 수정 diff는 의도한 차이를 비교적 명시적으로 드러내고 공개 trigger도 제공된다. Go가 AST부터 18/18인 천장 효과를 감안해야 한다. 이것을 Go 전체가 쉽거나 Python 전체가 어렵다는 결론으로 바꾸지 않는다.
- Python 자동 탐색은 저장소 manifest 내부로 제한되지만 Go는 native로 반환된 외부 stdlib/module 본문도 지원한다. Python N03의 functools 구현은 직접 제공에만 있다. Go는 CLI별 재초기화 비용, Python은 persistent RPC를 사용하므로 언어·서버·adapter 능력·저장소·결함 유형이 동시에 다르다. **이 실험으로 언어 자체의 인과 효과를 식별할 수 없다.**
- LSP에는 추가 코드 범위의 효과가 함께 들어가며, 동일 토큰 일반 검색 대조군은 이번에 없다. LSP 프로토콜만의 순수 효과나 다른 검색기 대비 우월성을 주장하지 않는다.
- 같은 조건/방향의 3반복 입력은 동일하고 응답만 새로 생성했다. Python N02의 LSP/search, N09의 AST/LSP, N05의 AST/직접 제공은 양방향 실제 입력이 같았다. 같은 입력에서 생긴 차이를 새 소스 획득의 효과로 설명하지 않는다.
- 비맹검 AI 수동 채점과 독립 AI 검토이며 독립 인간 평가가 아니다. 새 holdout·실서비스 MR·다른 언어에 대한 확증 결과가 아니다. Go witness도 사례에 따라 선택한 실제 함수·타입 대체물·소유권 모형이며 전체 프로젝트 통합 실행과 구분한다.

## 7. 채택 판단과 다음 개선 대상

**AST 문맥을 기본 구성으로 유지하고, 현재의 일괄 추가 탐색은 성능 개선 구성으로 채택하지 않는다.** 이번 결과가 지지하는 방향은 “더 많이 읽기”보다 **틀린 원인을 구분하는 데 필요한 본문을 선택하고 실제 입력까지 전달하기**다.

1. 변경된 값·조건의 직접 callee/소비자·타입 factory를 먼저 연결한다. 함수 앞쪽 첫 4개 호출이 초기화·정리 작업으로 채워져 핵심 호출이 후보에서 빠지는 것을 줄이는 정책을 별도 검증한다.
2. Python의 stub/위치에서 실제 stdlib·외부 API 구현/계약으로 이어지는 경로를 추가한다. N03는 실제 구현으로 API 오해를 바로잡을 수 있음을 보였지만 현재 자동 탐색은 그 본문에 접근하지 못한다.
3. 근거 ID와 허용 범위는 controller가 생성·검증하도록 해 모델이 긴 ID·범위를 임의 조합하는 부담을 줄인다. 의미적으로 관련 있는 근거인지 검증하는 일은 별도로 남는다. 현재 결과를 사후 보정해 이 개선의 성능으로 발표하지 않는다.
4. 정책을 고정한 다음, 국소 diff만으로 이미 풀리는 사례와 실제 외부 연결에 의존하는 사례를 사전 기준으로 분리하고 새 미사용 PR에서 확인한다. 이번 개발 자료에서 좋은 결과를 낸 사례만 선택해 성능을 확증하지 않는다.
