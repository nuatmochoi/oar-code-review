**3. 중요한 사례의 의미**

`LANdalf`에서 별도로 필요한 사실은 target framework에서 해당 Ping API가 취소 예외를 내는가이다. 새 LSP 근거는 생성자·DI 등록·BASE 서비스·테스트 등을 보강했지만 그 외부 API 계약을 제공하지 않았다. API 의미의 미확인은 정당하게 남겨야 한다. 그러나 취소 후 DB/SignalR 성공까지 필수화한 것은 더 넓은 영향 조건이다. 이미 offline인 장치에서는 `false == IsOnline`이어서 그 후속 갱신 없이 정상 반환할 수 있다는 좁은 경로를 따로 검토했어야 한다. 이 감사는 API 계약을 새로 입증한 것은 아니다.

`CrabTrap`의 기존 helper가 이미 query 실패를 nil로 반환했다는 것은 최종 보류의 실제 근거였다. 하지만 이번 변경에는 Count 결과와 `has_more`가 추가됐다. “과거에도 에러를 삼켰다”와 “새 페이지 정보가 모순을 만들지 않는다”는 다른 주장이다. 최종 판단은 새로운 projection 자체가 실패한다는 증명까지 요구하면서 새 소비 경로의 악화를 놓쳤다.

`apilix`는 부족한 소스를 더 받아야만 해결되는 사례가 아니었다. 계획에서 경로 탈출을 적었고, 최종에는 `startsWith(path.resolve(repoBase))` 코드가 전달됐다. 마지막 보고에는 5개 다른 경고만 남았고 이 후보의 처리 이유는 없다. 현재 schema는 계획의 모든 가설에 대해 최종 채택·기각·보류를 강제하지 않는다. 그래서 이 경우는 출력에서 사라졌다는 사실까지 확인되며, 모델 내부에서 어떤 이유로 선택하지 않았는지는 알 수 없다.

**4. 공식 채점 때문에 gold 소실과 경고 소실이 다를 수 있다**

공식 scorer는 경고의 대표 매칭 gold로 precision의 TP/FP를 정하고, 별도의 `covered_golden_indices`로 recall을 계산한다. 한 경고가 여러 gold를 덮을 수 있으며 항상 한 개만 허용하는 구조는 아니다. 실제 `gimmes`의 B1 경고는 대표 매칭이 FP G003이면서 coverage는 G003·G004였다. 이 때문에 FP 경고가 TP gold G004의 재현율에는 기여했다.

`Mcp-Docker`의 B1 anchor는 session.go, B2는 handler.go였다. B2에도 공유 Session의 token 덮어쓰기 원인이 남았지만, 공식 matcher는 state 진위 확인에 관한 다른 FP 항목 G014에 연결했다. G014의 반박은 “state가 존재하는지 확인하며 GitHub code는 1회용”이라는 내용이다. B2는 서로 다른 유효 code 2개를 조건으로 명시해 그 반박과도 범위가 다르다. 따라서 매칭을 독립 검토할 가치가 크다. 다만 이번에는 판정을 바꾸거나 B2를 확정 TP로 추가하지 않았다.

Codebase G041→G040, figlet G003→G005는 기존 정답을 놓친 동시에 다른 정답을 추가한 전이에도 나타난다. **관측 추가 5개도 모두 새 본문으로 새 결함을 발견한 5개라고 부르면 안 된다.** 원인 단위와 gold ID 단위를 따로 보아야 한다.

지표가 다르므로 자체 원인 F1과 공식 Grounded F1의 크기를 직접 비교할 수 없다. 이전 12개와 이번 25개가 겹치는 PR은 `gimmes`, `CrabTrap` 2개뿐이다. 이전 최종 reviewer의 SYSTEM 문장은 이번과 **정확히 동일**했다. 따라서 “더 엄격한 최종 SYSTEM으로 바꿨기 때문”이라는 설명도 맞지 않는다. 계획 단계의 추가, 입력 내용과 표본, 판독 방식, 생성 변동이 함께 달라졌다.

두 겹치는 PR을 보면 결과 차이가 더 명확하다.

- `CrabTrap G002`: 이전 AST의 2번째 반복은 맞혔지만 LSP는 세 반복 모두 이 항목을 보고하지 않았다. **전체 F1이 오른 이전 실험에서도 같은 손실이 있었다.**

또 이전 직접 연결 사례는 별도 상태 갱신 함수나 HTTP 입력 처리 함수의 새 본문이었다. 이번 손실 PR의 추가 자료는 Codebase의 pathlib, Mcp-Docker의 slog, apilix의 App.tsx, 또는 위치 metadata에 치우친 경우가 있었다. 자료가 늘어도 그 질문의 핵심 구현·외부 계약이 늘어난 것은 아니다. 그러나 그 추가 자료가 하락을 유발했다고 확정하려면 자료만 제거·복원하는 통제가 필요하다.

**6. 장표 12의 새 LSP 실행과 장표 13의 기존 LSP 기준은 무엇이 같은가**

여기의 “12”는 **장표 번호**이며 개발 12개 PR 또는 소실 12항목과 구분한다. 장표 13은 과거 공식 25 PR의 A 조건(22.60%)으로, 후속 후보 추가 실험이 그때의 보고 40개를 출발점으로 썼다. 장표 12에 있던 새 B2 조건은 17.92%였다.

**7. 다음 수정의 우선순위**

1. **계획 가설마다 최종 처리 결과를 연결한다.** 채택·기각·보류·다른 경고와 병합 중 하나와 이유를 남긴다. `apilix`처럼 조용히 사라지는 항목부터 막는다. 이전 FP까지 무조건 보존하는 정책은 피한다.
2. **좁은 결함의 필수조건과 더 넓은 영향 조건을 분리한다.** LANdalf의 취소 전달과 DB 저장 영향, CrabTrap의 기존 helper와 새 소비 경로를 따로 판정한다. 미확인은 반증이 아니다.
3. **계획에서 발견한 미확인 질문을 실제 조회로 연결한다.** 이번 비교는 이미 수집한 고정 자료를 넣고 계획만 작성했다. Market의 volume producer, 해당 환경의 API 계약처럼 질문에 필요한 자료를 받아야 한다. 무관한 정의·본문을 더 넣는 것으로 대신하지 않는다.
4. **원인 단위와 gold 매칭을 분리 감사한다.** 병합 경고는 여러 gold coverage를 점검하고 의심 매칭은 독립 판독 대상으로 삼는다. 기존 공식 점수와 보조 감사는 별도 보존한다.
5. **같은 자료·고정 계획/새 계획·리뷰 1회/2회와 반복 실행을 통제한다.** 현재도 입력 근거가 정확히 같은 6 PR에서 계획이 6/6 달라지고 finding은 5/6 달라졌다. 한 번의 점수 변화를 조회 효과만으로 해석하면 안 된다.

이번 작업에서는 위 후속 실험을 실행하지 않았다. 감사 비용은 추가 모델/native API 호출 0회다. 동결 파일 405개와 감사 입력 해시를 검증했고, 의미 분류와 기계적 확인을 분리해 기록했다.
