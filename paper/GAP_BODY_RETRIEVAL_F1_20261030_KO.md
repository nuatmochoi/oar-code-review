# 누락 본문 조회 개선: 원인·근거 F1 비교

2026-10-30 · 신규 최종 판단90개 · 기존 결과 보존

**누락 연결 중심 탐색은 기존 탐색보다 원인 F1을40.00→52.17, 재현율을26.67%→40.00%로 높였다. 그러나 오탐도1→2건으로 늘었다.** 근거 F1은30.00→34.78이다. 본문 확보와 실제 전달 문제를 보완한 효과는 일부 사례에서 확인했지만, 오탐 감소와 일반 성능 개선을 입증한 단계는 아니다. 손실을 보고 고른5PR의 진단이며 주 비교의 F1 차이95% 탐색 구간은 **−18.18~+46.04%p**로 넓다. 현 정책은 개선 후보로 유지하고 기본 방식 채택은 보류한다.

## 1. 무엇을 비교했나

| 실제 기능명 | 내부 식별자 | 마지막 판단 전에 수행한 작업 |
|---|---|---|
| 기존 문맥 그대로, 추가 조회 없음 | replay | 직전 예산 진단의 repaired_full 입력을 그대로 주고 새 final 생성 |
| 기존 후보에서 탐색 이어가기 | frontier | 기존 BodyFrontier 후보와 critic 전체 JSON의 단어 기반 우선순위를 유지해 조회 |
| 비평의 누락 연결을 중심으로 탐색 | gap | 명시적 누락 표현을 실제 공급 코드의 사용 위치에 연결해 후보 생성·우선 조회, 이후 동일 frontier 사용 |

첫 행은 **diff-only 대조군이 아니다.** 이미 AST·LSP·이전 추가 탐색·저장된 비평/검증 정보를 받은 문맥에서 *이번 추가 조회만 하지 않은* 대조군이다. 이전 diff→AST→LSP 실험의 전체12개 점수와 이번5개 점수를 같은 모집단처럼 합치지 않는다.

N03/N06/N07/H05/H10의 양방향×저장3반복=30개 prefix에3조건을 적용했다. 각 조건30리뷰 중 결함15·안전15다. H05/H10은 원래 추가 사례 분류에 속하지만 이번에는 이미 사용한 사례다. 새로운 미사용 검증이 아니다. 저장된 최초 판단·비평·probe는 고정하고 **마지막 판단만 조건별1회 새로 생성**했다. 저장 반복3개는 같은 새 입력을3회씩 재샘플한 실험과 다르다.

주 비교는 누락 연결 중심 탐색−기존 탐색이다. 두 조건 모두 비평을 사용한다. 새 정책은 후보 생성·우선순위·읽기 구간 선택·탐색 깊이 차이를 포함한 묶음이다. 기존 탐색은 기존 depth3와 완료 chunk 계획을 유지하고 새 정책은 별도 depth3 상한 없이 예산에 맞춰 구간을 줄일 수 있다. 따라서 비평 사용 여부나 우선순위 하나의 순수 ablation이라고 주장하지 않는다.

공통 조건은 다음과 같다.

- **추가 조회 최대6회:** 위치 조회와 본문 읽기의 합계다. 실패·empty도1회이며 개수를 억지로 채우지 않는다. 과거 조회에 더한 신규 예산이므로 원래 end-to-end 총6회 실험과 다르다.
- 실제 Pyright LSP 위치 조회→관측→본문 읽기→재계획을 마지막 모델 호출 전 한 단계에서 이어간다. 추가 LLM 판단·debate·probe·finding 필터는 넣지 않았다.
- 본문 chunk최대200행, HEAD+BASE 전체 누적 소스 union상한5200 reference tokens. 최초 실제 공급 소스147~3264토큰을 삭제·압축·퇴출하지 않았다.
- 기존 역할·지시·schema·causal_review_state 원문은 세 조건에서 동일하다(state cap5120). 새 위치 metadata는 보내지 않고 새 본문만 상태 앞에 삽입했다. 원래 metadata cap800을 유지했다.
- gpt-5.6-sol/low, 동시4개·시작 간격3초. 실제 데이터 조회 전 정책을, 모델 실행 전 준비 입력·코드·채점 계약을 고정했다.

## 2. 전체 비교표

F1은0~100 척도, 재현율·정밀도는%다. 원인 TP는 정확한 실패 연산과 영향을 설명한 최종 finding이며, 근거 TP는 여기에 필요한 실제 본문·호출·타입·소비 연결까지 공급된 경우다. FP는 결함/안전 양방향의 원시 finding 수에서 TP를 뺀 값으로, **결함을 지적했어도 원인을 틀리면 FP**다.

| 실제 기능명 | 원인 TP | 원인 FP | 미탐 FN | 원인 정밀도 | 원인 재현율 | 원인 F1 | 근거 TP | 근거 F1 | 안전 방향 경고 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 기존 문맥 그대로, 추가 조회 없음 | 4 | 2 | 11 | 66.67 | 26.67 | 38.10 | 2 | 19.05 | 0/15 |
| 기존 후보에서 탐색 이어가기 | 4 | 1 | 11 | 80.00 | 26.67 | 40.00 | 3 | 30.00 | 0/15 |
| 비평의 누락 연결을 중심으로 탐색 | **6** | 2 | **9** | 75.00 | **40.00** | **52.17** | **4** | **34.78** | 0/15 |

세 조건 모두 출력 실패0, 명시적 전체 리뷰 판단 보류0이다. 일반 테스트 권고나 근거 부족은 전체 판단 보류와 구별했다. 안전 무경고가 모두 충분한 소스에 기초한 안전 입증이라는 뜻은 아니다. 충분한 안전 근거로 인정한 건수는 세 조건 모두3/15다.

주 비교의 원인 TP는+2, FP는+1, FN은−2다. 재현율은+13.33%p이고 정밀도는−5.00%p다. 추가 조회 없음과 비교하면 원인 TP+2, FP는같은2건, 원인 F1+14.08%p다. **추가 조회 없음보다 오탐을 늘리지 않았으나 기존 탐색보다 오탐을 줄이는 목표는 미달**이다. 안전 방향의 새 오경고는 없으며 FP는 N03의 잘못된 실패 연산 설명에서 발생했다.

조건별 pooled F1은 `2TP/(원시 finding 수+결함 수)`로 계산했다. 근거 F1의 FP는 정확한 원인을 찾았어도 필요한 소스 연결이 부족한 finding을 포함하므로 원인 FP와 다르다. 충분 근거가 없다는 판정을 실제 결함이 없다는 뜻으로 바꾸지 않는다.

각 PR의 결함 방향3회에 대한 정탐 수다. 표의 `원인/근거`는 F1이 아니다.

**가장 분명한 본문 보완은 H05다.** 기존 b_r1/b_r3은 get_language_from_path의 header나 위치만 있었고 새 정책은 실제501–515 또는 기존501+신규502–515를 전달했다. regex match 실패→None 반환의 공백이 닫혀 두 새 finding의 근거 TP를 인정했다. 다만 추가 조회 없음 대조군도 이 두 경우의 원인은 이미 맞혔다. 이를 “아무 문맥 없는 baseline에서 놓친 결함을 새로2개 찾았다”로 포장하지 않는다. 새 정책이 근거를 닫았다는 증거와 원인 재현율의 변화를 구분한다.

**N07은 원인 탐지1건이 늘었지만 완전한 경로 입증은 아니다.** a_r3_gap은 실제 NDimArray.__len__164–178을 받았다. 다른 조건의 Tuple.__len__이나 위치 응답을 배열의 길이 구현으로 취급하지 않았다. scalar 생성의 정규화와 공개 Array 바인딩은 여전히 미제공이라 근거 TP0이다.

**N06·H10은 필요한 함수 선택이 남은 병목이다.** N06의 ask.py397–430은 실제로 마스킹된 문서·빈 줄이며, 다른 조회는 Wild나 posify 소비 호출부였다. H10은 evalf_prod/atan·적분 소비 함수 또는 전혀 다른 모듈의 NotImplementedError 발생 함수를 가져왔다. 실제 위치 조회와 본문 읽기는 성공했지만 필요한 가정 엔진·고정 입력의 호출/복구 경로를 대신하지 못했다. 이 구간을 호출 실패나 전달 잘림으로 설명할 수 없다.

안전 H05의 variant/get_languages/check_for_language가 확보된 경우도 해당 check의 참 값까지 공개 fixture가 제공하지 않아 정확한 두 코드 반환의 guard는 조건부다. 전체 카탈로그나 stdlib 구현을 새 요구조건으로 추가한 것이 아니라 실제 제공 본문의 미확인 조건을 안전 입증으로 대체하지 않은 것이다.

### 같은 입력의 응답 변동을 분리해야 한다

주 비교의30쌍 중 **4쌍은 실제 composed 입력 전체가 같다:** H10_a_r2, N03_a_r1/r2/r3이다. 각각 별도의 신규 final을 생성했으므로 표현뿐 아니라 판정도 달라질 수 있다.

특히 N03_a_r1은 같은 입력에서 기존 탐색 응답이 사용자 wrapper의 `f.__name__` 직접 접근 실패를 정확히 설명했고, 새 정책 응답은 `wraps(f)`의 metadata 복사가 실패한다고 틀리게 설명했다. `wraps`는 누락 속성을 건너뛰므로 동결 경계에 따라1/1 대0/0으로 채점했다. 이 손실은 **다른 본문을 검색한 정책 효과로 귀속할 수 없다.** 부모가 두 원문을 독립 판독해 별도 기록했다.

추가 조회 없음과 기존 탐색의 동일 입력도7쌍이고, 추가 조회 없음과 새 정책은4쌍이다. 예를 들어 H05_b_r3의 추가 조회 없음/기존 탐색은 같은 입력인데 한 응답은 원인을 보고하고 다른 응답은 reference에만 남겼다. 신규 sampling 변동을 숨기지 않는다. 동일 입력 여부 검사는 사후 기술 감사이며 주 비교나 표본을 재정의하지 않았다.

주 비교의 결함 방향15쌍은3승·1패·11동률, 안전15쌍은 모두동률이다. 승리 그룹은 H05_b_r1/b_r3, N07_a_r3이며 손실은 위 N03_a_r1이다. 과거 손실6그룹만 보면 이번 새 원인 정탐은 세 조건 모두1건이다. 그 부분집합에서1회복·1손실·4불변이므로 “과거 손실을 전부 회복했다”는 결론은 아니다.

## 4. 조회·전달·비용

위치만 받은 결과와 실제 소스 획득·예산 편입·입력 구성·성공한 모델 호출의 입력·최종 인용을 별도 감사했다. 실제90개 입력에서 기존 근거와 모든 추가 소스 행의 내용·경로·ID를 확인했고 잘림·변조는0이다. 추가 근거의 used_context 표기나 인용은 모델의 자기 보고이며 의미적 활용·정탐을 자동 입증하지 않는다.

본문 파일 읽기는 native 실행기 파일 읽기의 하위값이며 중복 합산하지 않는다. 서버 didOpen 관련 읽기는 별도29/36회다. 구조 index는 새 정책에서 frontier1614+selector283회다. Pyright subprocess 내부의 전체 파싱·index I/O와 CPU는 계측하지 않았다. 준비 시간은 로컬 병렬 실행의 관측값이며 서비스 latency 보장은 아니다. 각 리뷰 준비 시간의 합은 기존109.60초, 새 정책331.60초로, 실제 병렬 wall time과 다르다.

새 정책의 model 입력은 기존 탐색보다 적지만, 관련 없는 native 반환 후보를 펼치면서 controller 파일·index 접근이 크게 늘었다. **같은6회 상한을 같은 실제 연산량으로 해석하면 안 된다.** 단순 query 수 외에 반환 후보 수·index 읽기 비용을 제어할 필요가 있다.

신규 물리 모델 호출90회, 재시도0, 최종 실패0, 불완전 claim0, usage 미상0이다. 모델 총입력1,886,039·총출력141,725토큰이며 cache입력822,272와 reasoning출력16,845는 각각의 하위값이라 다시 더하지 않는다. 과거 initial/critic/probe/조회 비용은 이번 신규 비용 합에 포함하지 않았다.

## 5. 논문 method로 남길 부분과 다음 우선순위

method 후보는 **비평의 누락 연결을 실제 코드 위치에 묶어 수집하고, 실제 전달된 본문으로 완료를 판정하는 제어기**다. 흐름은 `비평의 누락 명제→공급 코드의 사용 위치→native 위치/구조 경계→본문→누적 예산 승인→실제 입력 감사→최종 판단`이다. 위치 성공을 본문 완료로, 본문 완료를 정확한 원인 검증으로 자동 승격하지 않는 점이 핵심이다. 현재 결과만으로 새로운 일반 성능 우위를 주장하거나 원 논문의 구현을 재현했다고 말하지 않는다.

우선순위는 다음과 같다.

1. **필요한 소비자·호출자·예외 처리 경로에 후보를 한정한다.** 동일 이름의 임의 참조보다 공개 trigger의 receiver·상속·호출 경로와 맞는 후보를 먼저 선택하고, native 결과 fan-out/index 비용을 제한한다. H10의 다른 예외 발생 함수, N07의 Tuple 길이 함수, N06의 posify 사용처가 필요한 소비자를 대신하지 않도록 한다.
2. **실행 본문 완료와 실패 연산을 검증한다.** 문서·빈 줄 chunk를 읽고 완료로 오인하지 않고, 필요한 남은 실행 구간을 이어 읽는다. N03에서는 `wraps` 자체의 복사와 사용자 wrapper의 직접 속성 접근을 구별하는 최소 반증 검증을 설계한다. 이 단계는 새 가설이며 아직 성능을 검증하지 않았다.
3. **수집 결과를 제어기 상태에 반영하는 효과를 별도 분리한다.** 이번에는 비교를 위해 causal_review_state를 고정했다. 다음에는 같은 수집 본문을 고정한 상태에서 신규 근거 ID·누락 충족 상태를 제어기가 갱신하는 조건을 비교해 오래된 “본문 없음” 비평의 영향을 확인한다.
4. 정책을 다시 고정한 뒤 기존12개 전체와 새 미사용 사례로 확장한다. 같은 실제 입력의 독립 final 반복을 추가해 생성 변동을 추정하고, 원인 F1·재현율 상승과 FP 감소를 함께 확인한다. source/native/파일 읽기 예산도 맞춰 비용을 비교한다.

현재는 예산 확대만으로 채택하기보다 **관련성 있는 경로 선택과 오원인 반증**을 먼저 고치는 것이 타당하다. H05의 실제 source closure는 보존할 개선 근거다. N06/H10의 남은 공백과 N03의 오원인은 다음 실험이 해결해야 할 실패 유형이다.
