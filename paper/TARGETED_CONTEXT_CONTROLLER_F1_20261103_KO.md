## 4. 구현한 method와 동일 조건

- **연결 우선 수집:** 공개 계약의 API/타입 entrypoint와 변경 표현식에서 외부 API 구현·생성자·import/export·상속/프로토콜·callee·소비자를 우선 수집한다. Python은 Pyright 정의/stub에서 검증된 실제 stdlib 구현으로 잇고, Go는 persistent gopls 세션으로 실제 정의·참조·구현 위치를 조회한다. AST/import/member fallback과 native provenance를 구별한다.

- **본문 단위 예산 관리:** HEAD+BASE source 합집합 5,200 o200k reference tokens 이내이며 공통 AST+LSP 행을 보호한다. 조회 6회 제한은 없다. 깊이·후보·동적 미해결·예산 거절은 trace에 남긴다. 선언 위치나 frontier 소진을 완전한 소비 경로 증명으로 취급하지 않는다.

- **Controller 결속:** 모델은 짧은 근거 핸들과 위치 enum을 선택하고 controller가 동결 registry에서 ID·path·snapshot·범위를 채운다. raw/canonical finding 수와 본문은 1:1이다. 삭제·병합·의미 판정·근거 재선택·답변 보정은 하지 않는다. 알려진 핸들을 골라도 잘못된 원인이나 무관한 근거는 정답이 되지 않는다.

모델은 모든 조건에서 gpt-5.6-sol/low, 새 최종 판단 1회다. verifier/debate·강화학습·과거 모델 응답 재사용은 없다. 기존 추가 탐색은 직전 search **소스만** 정확히 재생하고 판단은 새로 수행했다. 이번에는 LSP 단독군을 추가하지 않았으며 기존 탐색과 우선 탐색 모두 같은 AST+LSP seed에서 출발한다.

이번 비교는 먼저 수집·동결한 문맥을 같은 최종 리뷰 모델에 공급하는 실험이다. 모델의 리뷰 중 실시간 도구 호출은 0회이며, 배포 프로젝트의 전체 agentic 상호작용을 종단간 재실행한 실험은 아니다. 개선 collector의 native 조회·본문 수집은 실제로 새 실행했다.

Controller 개입은 짧은 핸들·prompt·schema enum·canonical 결속의 묶음이다. 고정 근거 범위는 자유 인용보다 거칠 수 있다. 순수한 사후 문자열 교정 효과나 탐색 우선순위 하나만의 인과 효과로 해석하지 않는다. 같은 reference source 상한이어도 schema·포맷·본문 길이 차이 때문에 실제 provider 입력 토큰은 다르다.

실제 source 사용량도 늘었다. 12문맥 합계는 Python 기존 28,749→우선 탐색 43,892 reference tokens, Go 30,333→62,372다. 5,200 상한이 같다는 뜻이지 실제 공급량이 같다는 뜻이 아니다. 이번 결과는 우선순위·후보 생성·외부 API bridge·지속 세션·더 많은 본문 편입을 합친 정책 묶음의 효과이며, 동일 실제 토큰 수에서 우선순위만의 순수 효과를 분리한 실험은 아니다.

## 6. 소스 수집 비용과 실행 실패

새 우선 탐색은 Python native/RPC 361회, Go acquisition RPC 2,028회였다. Go 세션 초기화·종료를 포함한 client request는 2,052회, server request는 12회다. Go의 native 오류 2건은 함수형 struct 필드에 implementation 조회를 요청해 “var, not a type”가 나온 경우다. 모델 인증/네트워크 실패와 구분한다.

본문 수집 소요 시간 합은 Python 59.33초, Go 67.62초다. 언어별 12문맥을 한 번씩 수집해 3반복 및 두 인용 조건에 공유했다. Python 기록상 body read/admission 시도 606회·file read 272회이고, Go 편입 body 468개·controller unique source load 405개다. 수집기별 계수 의미가 달라 언어 사이 I/O 효율의 직접 비교에는 사용할 수 없다.

기존 탐색 비용은 직전 수집의 역사 측정값(Python native 559회·Go native CLI 238회)이며 이번에는 그 소스를 재생했다. 새 수집도 보호 LSP seed의 과거 비용을 상속한다. 이 값을 이번 실제 native 비용에 중복 합산하지 않았다. 별도 health/smoke·index·내부 I/O·평가 협업 모델·수작업의 미계측 비용은 0으로 간주하지 않았다.

2026-11-02에는 성공 5건 후 응답 없는 HTTP 429 실패 1건으로 전역 admission이 정지했다. 실패 PY_N05_b_targeted_r3는 그대로 남겼다. 2026-11-03 재개 때 물리 미발급이 증명된 GO06_b_targeted_r1의 세 파일은 원형 archive하고 예정된 첫 실제 호출을 수행했다. 이전 STOP과 기존 6건의 70파일 SHA도 보존했다. 첫 예정 작업 단독→12건 동시2개→나머지 동시4개로 재개했으며 동일 gate의 최소 시작 간격3초를 지켰다. 별도 모델 probe나 좋은 답을 위한 재실행은 없었다.

물리 시도·재시도는 wrapper가 발급한 CLI 프로세스 기준이다. 429 메시지에 나타나는 CLI 내부 HTTP 재시도 횟수는 별도 미계측이므로 wrapper 재시도 0을 HTTP 요청 1회로 해석하지 않는다.

이 429 실패는 수정 방향의 무응답이다. 전체 리뷰 수와 실패율에는 포함하지만 원시 finding이 없으므로 F1 정의상 FP나 FN을 추가하지 않는다. 따라서 실패열과 사용량 미상 건수를 F1과 함께 확인해야 한다.

## 7. 판독 경계와 한계

Django(PY_N03)의 정답은 이름 없는 partial을 캡처한 사용자 wrapper가 나중에 f.__name__을 읽다 실패하는 경로다. functools.update_wrapper는 없는 속성을 skip하므로 wraps 자체가 예외를 낸다는 경고는 오원인으로 채점했다. 배열(PY_N07)은 len(a)=0이라는 실제 핵심 실패가 맞으면 전체 목록 미완성을 이유로 탈락시키지 않았다. 잘못된 부수 설명은 판정 이유에 남겼다.

Python Point의 동일 타입 경고나 Go logger의 BASE부터 있던 문제처럼 고정 공개 계약에서 새로 도입된 결함이 아닌 경고는 오탐으로 남겼다. blank/docstring/무관한 연산 위치와 존재하지 않는 ID도 자동 보정하지 않았다. 위치는 추가된 줄만 허용하는 규칙이 아니라 실제 관련 실패 연산이라는 기준으로 판독했다.

일반 source ID 인용은 실제 제공 unit 내부 범위로 검증한다. DIFF는 직전 실험과 같은 관련 hunk overlap 허용을 유지하며, 실제 관련 연산과 위치를 판독한다. 기존 자유 인용 prompt가 DIFF 좌표를 명확히 정의하지 않아 실제 HEAD 행과 diff 표시행을 모두 실제 참조 코드에 대조했다. N02 diff r2와 N10 AST r1/r2는 표시행 해석으로 삭제/실패 연산을 참조하며 finding 위치는 실제 HEAD다. 뒤늦게 HEAD-only 또는 full-containment gate로 탈락시키지 않았다. GO04_a_ast_r2의 1행 overhang 초기 판독 오류는 독립 검토로 수정했고 원래 grade bytes·전후 SHA·사유를 receipt로 보존했다. 다른 연산만 단독 지목한 실제 finding 위치 오류와 이 범위·좌표 예외는 구분한다. 이 모호함도 후속 HEAD 번호 명시 실험의 이유다.

수동 원문 판독과 독립 AI 검토이며 인간 맹검 채점이 아니다. Python·Go는 저장소·결함 유형·수정 방향 구성·난이도가 함께 달라 언어의 인과 효과를 분리하지 못한다. 같은 12개 개발 PR에서 얻은 결과이고 새 미사용 표본 검증은 포함하지 않는다. 작은 표본의 반복 최고점이나 본문 확보율만으로 채택을 정하지 않는다.

## 8. 위치 선택을 보강할 다음 설계

사용자의 추가 질문에 따라 제안한 후속안이며 이번 동결 실험에는 적용하지 않았다. 현재 controller도 행 ID를 실제 위치에 결속한다. 남은 문제는 번호 계산과 의미상 연산 선택을 구분해야 한다.

1. **diff HEAD 번호 명시:** unified diff 각 HEAD 행에 실제 번호를 표시한다. 동일 코드 정보의 표현만 바꾸는 가장 작은 변경으로, diff-only의 인접 행·docstring 오지목부터 비교한다.

2. **AST 연산 핸들 선택:** 모델이 임의 행이나 함수 전체 대신 실제 연산 ID와 코드 조각을 선택하고 controller가 snapshot·파일·AST 범위를 채운다. 예를 들어 q*=p.q와 p=Rational(p)를 별개 후보로 보인다. 변경 지점, 실제 실패 연산, 리뷰에 표시할 HEAD anchor를 구별해 외부 callee에서 실패하거나 삭제 때문에 발생한 결함도 표현한다. CORS/Logging 순서 문제는 한 줄 대신 두 등록 연산의 순서 관계를 선택하게 한다.

3. **설명–연산 대조:** 보고한 실패 유형·값 흐름과 선택 연산의 read/write/call 관계가 맞는지 확인한다. 정확한 코드 조각 일치와 AST/LSP 연결 검사는 기계적으로 확인하되 의미 정답을 보장한다고 주장하지 않는다. 불일치 교정은 별도 예산 안의 재확인 조건으로 실험하고 원시 보고·교정 이력·보고 수를 보존한다. 가까운 변경 줄로 일괄 이동하거나 조용히 경고를 삭제하면 점수만 바뀔 수 있다.

비교 순서는 현재 방식→HEAD 번호 명시→AST 연산 선택→설명–연산 재확인이 적절하다. 같은 사례·동일 총 토큰 예산에서 원인 내용 F1, 위치만 틀린 비율, 유효 원인 F1, 원시 FP·재현율을 함께 측정해야 한다. 이번 점수에 사후 보정을 적용하지 않았다.
